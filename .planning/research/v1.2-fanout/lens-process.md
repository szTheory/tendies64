What was wasteful (versus what paid off). Not wasteful: the late independent 5-lane review found the digest-completeness gap, an importer bounds hole and the timeout-vs-wrapper mismatch that no self-comparing test could see. Wasteful:

1. Review and verification ran once, at the end of the phase. CR-01 (combiner block and coverage table absent from state) was already an "open finding" at 09-09.1 but only closed after the review. Phase 10 touches exactly that state, so the review must be per-wave, not per-phase (see 1c).
2. Pins keyed to the wrong granularity: whole-manifest hash in the owner-gated oracle request (5 rebinds), whole-inventory pins (`f2-identity-pins`, 224-name snapshot, 45-of-45 CTest-name budget), bound-source tuples. Each new fixture or test moves several pins.
3. One test dominating the sanitizer wall (97%) and a 600 s wrapper nobody compared to measured seconds.
4. Hosted-only defect classes found after a push: Linux compile, post-Gate emit steps, TIMEOUT headroom. All three have local replays now (F-102, F-107, F-108); they must be mandatory preflights, not recalled lessons.
5. Plans too large (executors 40 to 95 min); the retrospective already says so.

### 1c. Concrete changes for v1.2 (each keeps the evidence)

1. Make three Phase 9 lessons into one scripted `scripts/preflight` (or a named gate step) that runs in under about 90 s and is cited by every plan's verify block: (a) `scripts/verification-scope.mjs --base <last-tested>`; (b) the act-image Linux compile (~50 s); (c) the post-Gate step replay (~20 to 25 s); (d) TIMEOUT audit (registered TIMEOUT vs max of native, ASan, hosted seconds, F-108); (e) `ctest -N -R` count check of plan regexes; (f) `ctest -R harness.rdp-oracle-authority` after any manifest edit; (g) tree PII scan plus rights scan; (h) `gh run list` for the current head before any 25 min native run. Today these live as prose in AUTONOMY.md; v1.1 defects 101/102/107/108 each cost a hosted cycle (5 to 7 min wait plus a context round trip) because a prose lesson was not run. Expected saving: most of the 5-in-21 red hosted runs.
2. Resolve the oracle-pin coupling before the first manifest edit (see owner-stop item A below). Otherwise Phase 10 will re-enter the exact 5-rebind loop (depth fixture, VG vectors, composite fixture and Phase 12 homebrew all add manifest rows).
3. Split `unit.core.state.import` first (plan 10-01 or earlier). F-110 already says a faster rehearsal "needs it split, which the 45-name budget forbids until Phase 10". CORE-06 enlarges state (combiner block plus coverage table, flip-every-member completeness test over 472 reachable members, field-use scan currently sees 72), so the ASan cost scales up. Without the split the sanitizer stage will approach the 3,000 s wrapper again; the plan must also set a fresh per-phase CTest-name budget (the 45 was Phase 9's own).
4. Review per wave. Each plan that changes state, digests, descriptors or the public header gets a scoped diff review (scratch `git archive` clone, never in the shared tree) before the next plan builds on it. Keep the one end-of-phase audit, but it then only re-checks open rows. This is the main lever on the 13 h review/fix tail.
5. Plan size cap in the discuss/plan prompt: at most 4 tasks, about 45 min executor time, one cohesive verified commit per task group. No decimal plans unless a hard stop; reserve one "fix-forward" plan slot per phase instead.
6. Native qualification only once per phase on the final source (the AUTONOMY rule already forbids rehearsing a red head). Reuse unchanged evidence via `verification-scope.mjs`. A metadata-only commit must not rerun native.
7. Docs and planning commits: always `[skip ci]`; the autonomous run's GSD commits (`gsd-tools commit`) do not add the tag by themselves. Verify that the planner/executor commit messages include it (v1.1 shows 157, but F-114 shows at least one docs-only push that ran full CI). Consider the cheap docs-only job from F-099.
8. Evidence retention: at each phase close, tar plus hash closed-phase run directories out of `build/gate` (receipt in the tree), and add a load check (`uptime` 1-minute load below ~6) in front of the native qualifier and the full gate. The F-112 recommendation (record host load, do not run heavy work during qualification) applies to parallel executors too.
9. Serial execution: `parallelization: true` with `use_worktrees: false` shares one git index and one build tree; v1.1's own lessons (git index reservation, F-102 build-graph race, reviewer `ninja -t clean`) came from that. For an unattended run set `parallelization: false` (v1.1 kept the 13 coupled plans sequential anyway).

## 2. Phase boundaries and success criteria

### Phase 10 (carry-in closure): right ordering, mostly verifiable, one over-broad criterion set

- Ordering is correct: state, digest and descriptor changes close before the freeze. Within the phase use this order: VER-06 (tests only) and GATE-01 step-1 (ordering plus dup-step removal, saves ~80 s per hosted macOS run for every later push) -> VID-07 (adds depth sidecar semantics) -> CORE-06 (exports it) -> RUN-07 (composite fixture using the final state) -> GATE-01 measurement last. VID-07 before CORE-06 matters because both change the exported state; doing them in the other order exports it twice.
- Biggest hidden coupling: Phase 9's `harness.phase09-qualification` (in every gate) pins the F2 identity table, the 159-case inventory snapshot and bound source tuples. A state/digest change (v25 to v26) will move those pins, plus 58 section goldens, a 67-member audit, sealed-body digests and membership sites. The plan should start with a "pin impact map" task (use `scripts/verification-scope.mjs` and `scripts/list-membership-sites.py`) that lists every pin a version bump moves and which are retired vs preserved (v25 stays readable?). This is a seconds-long check that prevents a long-gate discovery. Add it to the success criteria.
- SC1: the "byte-identical, or versioned under the compatibility policy" disjunction passes either way. Tighten: list the 17 pre-Phase-9 ids (must be byte-identical, 510 digests per the v1.1 audit) separately from descriptors 11/12 composites (must change, because depth activation changes output), and require the change record. A negative control exists (wrong-depth). Independence: expected values must be hand-derived from the primary RDP documentation (no oracle, D5); require a second independent derivation (the adversarial pass) because the VG-01 gap was exactly an unpinned Z edge.
- SC2: verifiable (digest equality of continued vs uninterrupted run, version marker, flip test). Cost risk, see 1c-3. Also state in the criterion which refusal remains (importer bounds from 09-09.1).
- SC3: good (named VG items). Note ID collision: Phase 9's review used VG-01..VG-11 too; reference them as "Phase 7 VG-xx" (07-VERIFICATION.md lines 118-134) so verifiers do not mismatch.
- SC4 (RUN-07): needs a negative control per output (wrong video byte, wrong audio byte, wrong digest, wrong save byte each fail). Add it. Needs a new authored guest ROM: schedule its pinned-Binutils build early (cheap actual consumer first, per AUTONOMY).
- SC5 (GATE-01): flawed as a pass/fail on a noisy sample. Planned savings (~42 s duplicate audio step + ~40 s CTest cost ordering) take the cold projection from 673 s to ~590 s, a ~10 s margin against a ~50 s spread; F-111 itself says to judge by cache freshness and spread, not another candidate cycle. Also a genuine cold run only happens on cache eviction (7 days idle) or key change, and would be cancelled by the 10 min limit, i.e. a red main. Recommended criterion: (a) the two changes landed with before/after step timings from two hosted runs; (b) `timeout-minutes` for gate-macos raised to 15 (a one-line owner-visible change F-114 already floats) and (c) one forced cold run (delete the cache with `gh cache delete`, then rerun) completes inside 15 min, with the measured value recorded; (d) a test that pins outer-limit relations for qualify-audio.py and qualify-phase09.py (F-106's "record the limits" is vague as written). Producing a cold run needs a cache deletion on the public repo; that is not an owner stop but note it in the plan so it is not treated as destructive.
- ci.yml is bound source: editing it moves frozen identities for Phase 8/9 qualifiers and the policy scanner (`check-ci-yml.sh`); run the scanner and `act -n` locally first.

### Phase 11 (installed consumer and freeze): under-scoped and under-researched

- The present public facade (`core/include/tendies64/t64_facade.h`, 57 lines) is a provisional two-function ops table (advance, drain_guest_log), still saying "the API freeze is Phase 10" (stale). `t64_machine.h` (672 lines) is the internal machine contract, not a C-ABI instance API. CMake has no `install()` rules at all (`core/CMakeLists.txt` only has `add_library(t64_core STATIC ...)`). So API-01 is greenfield design (lifetime, profile selection, transactional admission, timed input, bounded advance, rings with backpressure, reset/unload, three error classes with ABI-width types), plus new packaging, plus the consumer, plus ABI-identity tooling, plus the freeze. "Research: MODERATE" understates this; run the discuss fan-out with explicit API-evolution, ABI-identity, error-model and ring-semantics lenses (AUTONOMY already mandates fan-out). Consider splitting into 11 (instance API implemented and exercised in tree) and 12 (install package, independent consumer, freeze), renumbering the host phase to 13. If the owner keeps three phases, cap each plan and keep the freeze as the last plan only.
- SC1: define "independent" in CONTEXT before planning: separate source tree and CMake project, built only against `find_package` of a relocated install prefix, no `core/` internal headers, ideally compiled by a different compiler than the core (clang vs gcc) to catch ABI assumptions. "Mismatched version" must be an ABI/API version constant, not a release version (D6 forbids tags/versions); write that into the discuss record so it does not become an owner stop.
- SC3 and SC2: fine, add negative controls the roadmap already names. SC4: reuse the existing determinism lint objects (ADR-0006) and add an `nm -u` allowlist on the installed archive. A static archive has no dynamic import list, so say "undefined symbols of the archive" explicitly.
- SC5: add (a) a mutation control (edit the frozen header: the check must fail), (b) the freeze record's additive-extension rule and amendment procedure. Otherwise Phase 12 can discover a missing call (host clock, audio backpressure, input timing) and be blocked by its own freeze, an unplanned hard stop in an unattended run. A cheap mitigation is a "host-loop-shaped" probe in the Phase 11 consumer (frame loop pulling video/audio rings with an injected clock) so API fit is tested before the freeze.
- PII: relocation tests naturally print absolute install prefixes; normalise to `$PWD`/relative paths in evidence (AUTONOMY already hit this in Plan09).

### Phase 12 (host and playable): over-scoped and contains owner stops

- SC2 "a physical controller mapped by the host moves the game" and "plays in a minimal host window" need a human and owner-held hardware (AUTONOMY section 4: physical testing with owner-held hardware) and a display. They are not headless-verifiable. Rewrite as automated and owner-optional: SDL3 `dummy` video and audio drivers plus SDL's virtual joystick API injects pad events; the criterion is "scripted virtual-joystick input yields the same guest result and digest as the headless run" (already SC2's second half). Move the physical-controller smoke to an explicit optional owner checklist outside the must-haves. Reason it matters: in `/gsd-autonomous`, a `human_needed` verification asks a question, and "continue without validation" records deferred verification and stops autonomous mode, which on the last phase also skips the milestone lifecycle (autonomous.md step 3d and 4).
- API-06 route B (libdragon GCC/newlib toolchain built from source) is a large build (tens of minutes per OS), needs package/provenance audits before first use, embeds newlib and libgcc code in a distributed ROM (D4 lists BSD-2 etc. as outside the copy allowlist; the existing AUTONOMY rule says a test ROM's repo license does not grant redistribution of the generated ROM), and has an open compatibility unknown: libdragon titles typically use rspq microcode, rdpq and joypad paths, far beyond the authored fixtures the emulator has run. Pre-resolve by choosing route A (authored here: assembler-built, pinned Binutils, existing fill/VI/SI paths, a moving-rectangle-on-pad title) as the required deliverable; route B becomes a research-only note in the LibFuturo/playable evaluation. The roadmap's Decision gates line "Pin the route B libdragon toolchain" should then be dropped.
- SDL3: a new dependency that needs the AUTONOMY legitimacy audit before first use (provider, provenance, purpose, lifetime). Local macOS has SDL 3.4.10 on disk (pkg-config), but ubuntu-24.04 has no SDL3 package, so a Linux CI lane would need a pinned source build, which conflicts with the CI cost rule. Make the host a local-plus-macOS-only optional build, outside the required fast gate; keep only "core builds with no SDL" and "build without host target" in the main gate. Do the dependency audit record in the discuss step, not mid-plan.
- "UI hint: yes" will make `/gsd-autonomous` run the UI design-contract step (3a.5) and UI review (3d.5), meant for web frontends; remove the hint or set `workflow.ui_phase` and `workflow.ui_review` false.
- API-07 (LibFuturo): good as research, but SC4 "a written evaluation exists" is not verifiable. Add: states the contract revision/date and URL checked, maps each contract point to a frozen API call or a gap, and a grep control that no LibFuturo dependency entered the build.

## 4. GSD configuration and launching the autonomous command

### config.json settings

Helps: `plan_check: true`, `verifier: true`, `code_review` (see below), `security_enforcement: true` (ASVS 1, block on high: right for untrusted ROM/state input and the new installed-consumer and SDL surface), `pattern_mapper`, `plan_review.source_grounding`, `human_verify_mode: end-of-phase` (no mid-flight executor halts), `mode: yolo`.

Hurts or needs attention for an unattended run:

1. `workflow.auto_advance: true` (persistent). `/gsd-autonomous` already drives discuss -> plan -> execute and calls execute with `--no-transition`; plan-phase step 15 (auto-advance-check.md) also chains into execute-phase when `auto_advance` is true. Result: plan-phase may execute the phase, then autonomous step 3c executes again (a no-op if everything is complete, but at best wasted context and at worst a second pass). Set `auto_advance` false for the run. `_auto_chain_active: true` is stale; execute-phase clears it when run without `--auto`, so harmless.
2. `workflow.code_review: true`. Autonomous step 3c.5 chains `gsd-code-review` and then `gsd-code-review --fix --auto`, which lets a fixer agent commit C changes unattended. The repo has sealed-body digests, reviewed-source rosters and frozen tuples; an automatic fix can move pins and trigger a fix cycle. Recommendation: set `code_review: false` for the run and rely on the project's own per-wave review plan task (scratch clone, five lanes at end of Phase 11 for the freeze), or accept review but not the auto-fix.
3. `workflow.nyquist_validation: true`. v1.1's audit reports nyquist `not validated` for all three phases (VALIDATION.md left draft). That pushes the final milestone audit to `tech_debt`, and autonomous step 5a then asks via AskUserQuestion ("Continue with tech debt / Stop"). Either run `gsd-validate-phase` per phase in the plan or set `nyquist_validation: false` (the repo has stricter native verification).
4. `parallelization: true` with `use_worktrees: false`: set parallelization false (see 1c-9).
5. Missing: `git.create_tag` defaults to true, so `gsd-complete-milestone` would create a `v1.2` tag. v1.0 and v1.1 have no such tags (only phase09-fh/fr/f2) and D6 says no version tag. Set `git.create_tag: false`. Also check there are no leftover local branches, since complete-milestone asks a merge question if any exist.
6. `workflow.ui_phase` / `ui_review` are unset (default on); with Phase 12 "UI hint: yes" they will fire. Set false.
7. Model profile `adaptive` with routing tiers (light xhigh, standard high, heavy high) is fine; claude-opus-5-5 mapped.

### Other prompts that will stall an unattended run (autonomous.md facts)

- Smart discuss (default when CONTEXT.md is missing) uses AskUserQuestion for "hard-to-reverse" technical choices and for product/preference questions, and greps `src/ app/ *.ts`. Phase 11's freeze-shape decisions are exactly hard-to-reverse. It also does not do the AUTONOMY-mandated fan-out and adversarial pass. Pre-write CONTEXT.md for each phase with the project's own fan-out discuss (as 09-FANOUT-*.md, 09-DISCUSSION-ADVERSARIAL.md did), then autonomous reports "Context exists, skipping discuss". For phases 11 and 12 the context can be produced right before they start (see the launch sequence).
- `STATE.md` "Blockers/Concerns" is read after every phase (step 4: "If blockers are found, go to handle_blocker"). It currently lists seven standing gates (VID-04, D2, D4, D6, D7, hardware, the Phase 9 oracle rebind note). A literal reading stops the run after Phase 10 with Fix/Skip/Stop. Retitle that section "Standing gates (not blockers)" or move them to Deferred before launching, and keep genuine blockers empty.
- `gaps_found` after verification: one gap-closure retry, then a prompt. `human_needed`: a prompt; "continue without validation" stops autonomous mode. To avoid both, give every phase a final review-fix-reverify plan (as 09-10) so verification runs after fixes, and keep human-only items out of must-haves.
- Audit result `tech_debt` or `gaps_found`: prompt (5a). Cleanup (5c) asks before deleting phase dirs. Handle blocker "Fix and retry" has a 3-attempt ceiling then `needs_human`.
- Recommendation: add a short "GSD prompt dispositions" table to `.planning/AUTONOMY.md` (gaps_found: run gap closure once; audit tech_debt with only documented items: continue; cleanup: archive per v1.1 precedent; standing gates are not blockers). AUTONOMY already tells the agent never to ask for routine approvals, so this removes ambiguity without weakening any owner stop.

### Recommended launch

Pre-launch (owner or orchestrator, before `/clear`): items in section 6 below. Then:

```
/clear
/gsd-autonomous --from 10
```

Notes on flags (from autonomous.md): `--from N` filters out lower phases; `--to N` halts after phase N and skips the audit/complete/cleanup lifecycle when later phases remain (resume text is printed); `--only N` runs one phase and never runs the lifecycle; `--interactive` keeps discuss inline and asks questions (do not use it); `--converge`/`--cross-ai` routes planning through cross-AI review and needs external AI CLIs (do not use; also cost/credentials). Without `--only`, after all phases the run executes `gsd-audit-milestone` -> `gsd-complete-milestone 1.2` -> `gsd-cleanup`. Omitting `--from` is equivalent today (Phase 10 is the first incomplete phase). Because the freeze is one-way and the session will compact more than once, a safer variant is two legs: `/gsd-autonomous --to 10` (stop for a short owner glance at the Phase 10 audit before the freeze), then after `/clear` `/gsd-autonomous --from 11`. If unattended end to end is the priority, run the single command above and expect at most one end-of-run prompt (audit tech debt).

Caveats: the run is one long orchestration session (v1.1 needed several context compactions); resume with the printed `--from` command and do not re-ask settled questions (AUTONOMY already says so). Smart-discuss and `human_needed` are the two places it can silently wait for input.

## 5. Over-/under-scoped items (summary)
