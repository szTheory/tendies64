# Pitfalls Research

**Domain:** Deterministic, accuracy-first Nintendo 64 emulator (Tendies64), greenfield
**Researched:** 2026-11-09
**Confidence:** MEDIUM overall. Licenses, repo state and fixture contents were checked directly against GitHub (HIGH for those facts). Hardware behavior rests on the n64brew wiki and test-suite READMEs (community references, MEDIUM, and the wiki has visible typos). Several CPU/FPU/TLB/cache items are architectural knowledge that was NOT re-verified against the NEC VR4300 User's Manual in this pass and are marked as such.

Phase names below are **provisional stage labels**, not a roadmap. The synthesizer should map them:

## Critical Pitfalls

These cause rewrites, false support claims, or rights problems. They are ordered by leverage on Tendies64's core value (evidence-backed claims), not by hardware subsystem.

### Pitfall 1: Emulator-vs-emulator agreement treated as hardware truth

**What goes wrong:**
Expected values come from ares, Angrylion-Plus, parallel-rdp or Project64 output. Tendies64 matches them, the dashboard goes green, and the project inherits their bugs. `[OD]` already says agreement with another emulator is not hardware accuracy; the trap is violating it by accident through "expected result" files.

**Why it happens:**
There is no hardware in the loop (physical measurement is an owner stop `[OD]`), so the nearest oracle is another emulator. parallel-rdp's conformance suite is bit-exact against Angrylion-Plus by design, and its README lists deliberate deviations where it makes undefined behavior deterministic (first-cycle CombinedColor/Alpha cleared, LODFrac ignored in 1-cycle, TexLOD ignored in copy mode, MemoryColor readable in blender cycle 1 of 2-cycle mode, etc.) `[PF: github.com/Themaister/parallel-rdp-standalone README, 2026-11-09]`. So even the "reference" is a modified reference. n64brew also notes that "Most emulators do get [CIC seeds] wrong" and that wrong values were copied between projects `[CR: n64brew PIF-NUS]`.

**How to avoid:**
- Every fixture manifest entry carries an `expected_result_provenance` enum: `hardware-derived (public, with console rev/region/flashcart/capture)`, `self-checking ROM (decides pass/fail itself)`, `vendor document`, `differential-vs-<emulator@version>`, `own-derivation`. Differential entries can never promote a support claim above "differential agreement".
- Prefer self-checking ROMs (nemu64-test decides pass/fail on-device `[CR]`) over image/hash comparison.
- Never copy a constant (CIC seeds, RCP/RSQ tables, RDP LUTs) from another emulator without an independent derivation test.

**Warning signs:**
Expected-output files generated by running another emulator in CI; a commit message "matches ares"; a conformance number reported without the reference version; RDP "pass" described as "accurate".

**Phase to address:** S0 (manifest schema + evidence tiers), re-enforced at S3/S4 whenever a differential suite is adopted.

### Pitfall 2: Hash-as-proof and "non-silent"/"boots"/"screenshot" as proof

**What goes wrong:**
A deterministic frame/audio hash is recorded, then used as the oracle. It proves repeatability only. A wrong renderer is perfectly repeatable. Likewise "audio is non-silent", "the logo appears", "boots to menu" are smoke tests, not accuracy evidence.

**Why it happens:**
Hashes are cheap CI checks, and determinism is a stated core value, so determinism evidence is easily mistaken for correctness evidence. `[OD]` AGENTS.md: "A boot, screenshot, test score, output hash, or agreement with another emulator alone does not establish broad compatibility or hardware accuracy."

**How to avoid:**
- Name hash tests as `regression-pins` in the manifest; they detect change, not error. Changing a pin requires a stated reason.
- Audio: a small authored diagnostic with defined event/sample expectations (e.g., known tone at known sample offsets relative to AI DMA start), not "RMS > 0".
- Support-claim template requires a column "oracle type"; hash/screenshot rows can only back "regression-pinned".

**Warning signs:**
Pins updated in bulk with "update golden"; a claim table where every row cites a hash; an audio test that only checks for non-zero samples.

**Phase to address:** S0 (claim/evidence template), S4/S5 (video/audio oracles).

### Pitfall 3: Green on empty (no tests ran, timeout, crash, missing fixture, wrong count)

**What goes wrong:**
The headless runner reports pass because: the ISViewer buffer was never written (empty = vacuous success), the ROM never finished (timeout swallowed), a fixture was missing and the step skipped, the suite ran 0 or fewer tests than expected, or the parser matched "Failed: 0" in a truncated line.

**Why it happens:**
nemu64-test's documented outcomes are three: `Done! Tests: 262. Failed: 0`, `Failed: N`, or **an empty screen meaning "the emulator didn't make it to the end"** `[CR: nemu64-test README]`. A naive runner treats absence of "Failed" as success. Also the suite's test list is feature-flag dependent (`base`, `timing`, `cycle`, `cop0hazard`, `poorly_understood_quirk`, `experimental_rdp`, stress tests `[IO: nemu64-test Cargo.toml @9a8b9f7]`), so "Tests: N" changes with build flags and commits.

**How to avoid:**
- Runner outcome enum, mutually exclusive and exhaustive: `pass | guest-fail | boot-fail | timeout | missing-fixture | harness-error` `[OD: PROJECT.md]`. Anything not positively matching the completion line with the pinned expected total `N` is not `pass`.
- Pin the expected total test count per (fixture, feature set); a count change forces a manifest edit.
- Mandatory negative controls in CI: (a) a ROM/expected-value pair that must fail, (b) an empty-output ROM that must classify `boot-fail`/`timeout`, (c) a deleted fixture that must classify `missing-fixture`, (d) a harness crash injection that must classify `harness-error`.
- Timeouts bound by guest time/instruction count, never wall clock (see Pitfall 7).

**Warning signs:**
Runner exit code 0 with empty stdout; CI duration suspiciously short; pass count `0/0`; any `|| true` in test scripts; a "skipped" status counted as success.

**Phase to address:** S0 (runner result protocol and negative controls before any emulator code).

### Pitfall 4: Experimental / timing / cycle test groups in the required CI gate

**What goes wrong:**
Tests the suite's own authors say are unstable or poorly understood become required-CI gates, so the project either chases phantom failures or quietly disables the gate. The reverse also happens: the gate is silently narrowed to the easy `base` set while claims imply more.

**Why it happens:**
nemu64-test's Cargo.toml documents it directly `[IO: Cargo.toml @9a8b9f7, 2026-11-09]`:
- `cycle` and `cop0hazard`: "There isn't much test coverage to fully derive the rules yet (and most likely this wouldn't be implementable by a dynamic recompiler)"; off by default.
- `poorly_understood_quirk`: "aren't enough to implement in an emulator yet"; disabled and "not even reported as disabled".
- `experimental_rdp`: filled-triangle RDP tests "aren't stable on hardware yet".
- `live_progress`: "has been seen to wedge real hardware".
- `timing`: requires accurate time (e.g., "a NOP is 0.5 cycles, Random decrements by 1 per instruction").
The upstream CI itself builds only `base` and `base-cycle-timing` ROMs `[IO: .github/workflows/build-rom.yml]`.

**How to avoid:**
- Three lanes, declared in the manifest per test group: `required` (self-checking, hardware-understood), `scheduled/advisory` (timing, cycle, stress), `research` (experimental, poorly understood). Promotion between lanes needs a written justification and evidence the group is stable.
- Report advisory failures; never let them block merges, and never let their green status inflate claims.
- Record the exact feature flags used to build each ROM in the manifest.

**Warning signs:**
A required job that is flaky; `continue-on-error: true` on a required job; claims citing `timing` pass without stating the timing tier of the core.

**Phase to address:** S0 (lane policy), S1/S3 when first suites land.

### Pitfall 5: Unpinned fixtures, toolchains and upstream sources

**What goes wrong:**
A fixture ROM or its build recipe changes underneath CI, or an upstream disappears. Results become non-reproducible and provenance is lost.

**Why it happens / evidence:**
- nemu64-test needs a Rust toolchain (via `rust-toolchain.toml`) plus `nust64` installed `--version 0.4.1 --locked`; the upstream CI comment says "Pinned: nust64 bundles the IPL3; an unpinned bump can break booting" `[IO]`.
- The IPL3 is sourced from libdragon, and **`DragonMinded/libdragon` shows "archived by the owner on Oct 1, 2026. It is now read-only"** on its GitHub page `[PF: github.com/DragonMinded/libdragon, 2026-11-09]`, although the last commit is 2026-09-14 and libdragon.dev still links to that repo. Where development continues is `[UNK]`; a Codeberg copy under a personal account and a SourceForge mirror exist and are not official `[CR: web search]`. nemu64-test links the IPL3 at `tree/preview/boot`, a moving branch name.
- nemu64-test HEAD at research time: `9a8b9f7d94ee2f6f57d7feed70c98c22cdc30e6c` (2026-09-08). This is a tip observation, not an audit.

**How to avoid:**
- Pin full commit SHAs, never branches/tags; record toolchain versions and `Cargo.lock` hashes; store the ROM digest and the build recipe.
- Mirror what you are permitted to (license-permitting) into project-controlled storage; record the mirror's retrieval date. Treat the archived libdragon as a frozen dependency: decide who owns IPL3 maintenance (`[OD]`: maintenance owner must be clear for copied code).
- Build fixtures from source in an isolated step and compare to the pinned digest; a digest mismatch is `harness-error`, not `pass`.

**Warning signs:**
`git clone` without a checkout of a SHA in scripts; `cargo install` without `--locked`/version; fixtures downloaded from "latest" release URLs.

**Phase to address:** S0 (fixture manifest + pinning), S2 (IPL3 ownership decision).

### Pitfall 6: Rights leakage through "open" test ROMs and committed binaries

**What goes wrong:**
A repository license (MIT, Unlicense) is assumed to clear every generated ROM and every embedded asset. It does not.

**Evidence:**
- nemu64-test is MIT `[PF]`, but its on-screen font source says "This font is based on Geneva 9 by Susan Kare" (`src/graphics/system_font.rs`) `[IO: read 2026-11-09]`. Third-party typeface/bitmap-design provenance is not covered by the repo's MIT grant `[INF]`. Its ROM also embeds the IPL3 via `nust64` `[IO]`.
- PeterLemon/N64 is Unlicense per GitHub `[PF]`, but the tree contains **408 prebuilt ROM files (`.n64/.z64/.v64`) and ~1,292 binary-looking assets (images, audio)** with no per-asset provenance `[IO: git tree, 2026-11-09]`. It also contains `BOOTCODE/BOOTCODE.BIN` and `LIB/N64_BOOTCODE.BIN` (4,032 bytes each; the .asm header reads "N64 'Bare Metal' NUS-CIC-6102 Boot Code by krom") `[IO]`. Whether that code is clean-room or a re-expression of Nintendo's IPL3 is `[UNK]`; treat it as rights-unknown and exclude it from the boot route.
- The Retro Regen suite forbids modification/rebranding `[OD: PROJECT.md; not re-fetched]`.

**How to avoid:**
- Fixture admission = (a) source rights, (b) **each embedded asset's** rights (fonts, images, samples, boot code), (c) build-tool-injected blobs (IPL3, libraries), (d) whether the *binary* may be redistributed or only built locally.
- Default to build-from-source in CI rather than committing ROM binaries; commit only digest + recipe. If a ROM cannot be cleared, keep it as `local-only` (not in public CI).
- Prefer authoring Tendies64-owned diagnostic ROMs (own font, own assets) for the permanent smoke lane; use third-party suites as pinned, built-on-demand, license-audited inputs.
- Never import PeterLemon's `BOOTCODE`/`IPL3Font` into any boot path or fixture set without a provenance audit.

**Warning signs:**
`*.z64` appearing in `git status`; a manifest `rights` field containing only "MIT"; assets with no authorship notes.

**Phase to address:** S0 (admission checklist), S2 (boot route), ongoing at every fixture adoption.

### Pitfall 7: Host-state leaks that destroy determinism

**What goes wrong:**
The "canonical core" gives different results across runs/hosts because something host-defined reaches guest-visible state.

**Where it leaks (checklist):**
- Wall clock / `time()` (RTC emulation: n64brew notes "most emulators ignore [RTC] writes and use host time" `[CR]`), host timers driving audio or VI.
- Uninitialized RDRAM/SRAM/PIF-RAM/RSP DMEM/IMEM/register file contents. Real RDRAM power-on contents are undefined; Nintendo's IPL3 does not clear all of it, while libdragon's IPL3 **does** clear RDRAM `[CR: libdragon boot/README]`. So the boot route changes guest-visible memory; the fill pattern is a named profile choice `[REC]`.
- Entropy: libdragon's IPL3 collects "true random" entropy into a boot flag `[CR: boot/README]`; in an emulator this derives from the timing model, so it is deterministic only if the timing model is.
- CP0 Random register, RDP noise/dither LFSR seed, COMPARE/COUNT start values.
- Host FPU (rounding mode, denormal handling, x87 vs SSE vs NEON), `-ffast-math`, FMA contraction; host SIMD saturation semantics differing between SSE/NEON/scalar in RSP vector ops `[INF]`.
- Threading: RDP/RSP/VI on separate threads with unspecified interleaving; GPU RDP results depending on vendor/driver (parallel-rdp lists driver-specific failures: AMD small-type arithmetic, RADV ACO needing `PARALLEL_RDP_SMALL_TYPES=0`, NVIDIA Linux caveats `[PF: parallel-rdp-standalone README]`).
- Hash-map iteration order, pointer-keyed ordering, ASLR, locale, uninitialized C/C++ stack, and `memcmp` of padded structs.
- Save/serialization state that includes host paths or timestamps.

**How to avoid:**
- Core takes only (profile, content, input events with guest timestamps, advance-by-guest-time budget). Everything else, including RDRAM power-on pattern and RTC base, is an explicit profile parameter.
- Soft-float (or carefully fenced) FPU, scalar-reference RSP vector semantics before any SIMD fast path, with differential tests scalar-vs-SIMD on random + stress vectors.
- Run every required test twice in different process environments (different ASLR, thread counts, host OS) and diff full-state digests at fixed guest times; run under sanitizers (MSan/Valgrind-style uninitialized-read detection) in a scheduled lane.
- A GPU RDP, if ever added, is a **presentation/optional backend**, never the canonical raw-output path: it conflicts with "no host dependency" `[INF/REC]`. The canonical RDP is a software reference (see Pitfall 17).

**Warning signs:**
"Flaky only on CI"; different hashes between macOS/Linux; test passing only with `-j1`; any `std::chrono`/`clock_gettime`/`rand()` in core.

**Phase to address:** S0 (determinism test harness), S1-S6 per subsystem; verify again at S7 with the installed consumer.

Code is copied from a GPL or restrictively licensed emulator "just to get unblocked", locking the (still undecided) Tendies64 license, or creating an unfixable provenance problem. `[OD]`: license/visibility/release channel are open owner decisions and a hard stop for publication; `[OD]` also prefers copy-with-provenance over dependencies, which raises this risk.

### Pitfall 9: Treating a libdragon IPL3 route as "boot solved"

**What goes wrong:**
Tests boot, so boot/PIF/CIC is declared done. In fact an open IPL3 tests only a narrow path, and the emulator may hide real-hardware boot requirements.

**What the open IPL3 does and does not cover `[CR: libdragon boot/README, n64brew IPL/PIF pages]`:**
- It performs RDRAM init/config, loads an appended ELF (compressed supported), clears RDRAM on cold and warm boot, collects entropy, accepts ROMs of any size with no header checksum, ships "dev" and "prod/compat" builds, and reads boot flags from IPL2 (`s4` = TV type, `s6` = ROM seed; iQue differs) `[IO: boot/ipl3.c]`.
- Its production/compat builds are brute-force "signed" to satisfy **CIC-6102** checksum `[CR]`; it says nothing about CIC-6101/7102, 6103, 6105, 6106 seeds or the 6105 challenge/response handling.
- Nintendo's IPL3 always loads a hardcoded 1 MiB and uses the header check code (not a CRC) `[CR: n64brew ROM Header]`. Libdragon's IPL3 is "not meant to be a replacement for software not designed for it".
- It says nothing about IPL1/IPL2/PIF-ROM behavior: the PIF checks region, IPL2 sends the checksum, PIF halts the CPU via NMI on mismatch; the game must send command 0x08 within ~5 s or the PIF halts the CPU, then a continuous challenge/response loop runs `[CR: n64brew PIF-NUS]`. An emulator that never models any of this will never see the failure modes.
- nemu64-test bring-up hints show IPL3 exercises: RDRAM init skippable via `RI_SELECT` nonzero; an RSP DMA from RDRAM addresses above 8 MiB reads zeros ("there is no RAM mirroring"); an IMEM-to-RDRAM DMA longer than 4 KiB wraps inside IMEM `[CR: README]`. Those are device behaviors, and a "just HLE the boot" shortcut skips them.

**Why it matters:**
HLE boot must hand the game exactly the CPU/COP0 registers, DMEM/RDRAM/low-memory state (boot flags, TV type, memory size) that IPL2/IPL3 would. Wrong guesses are copy-pasted between emulators `[CR]`. IPL3 variants also affect actual entry (CIC 6103 subtracts 0x100000, 6106 0x200000 before jump `[CR]`).

**How to avoid:**
- Name the boot route in the profile: `boot=libdragon-IPL3@<sha> over modeled PIF-lite` or `boot=documented-HLE@<spec>`. Support claims state it. Everything IPL3-dependent (CIC variant, seeds, TV type register, reset type) is a profile field with a test.
- Boot to the *libdragon IPL3 execution* (real code, real RDRAM init path) before adding HLE shortcuts, so shortcuts are differential-tested against the real path.
- Write a "boot limits" doc listing unmodeled behaviors (PIF challenge, NMI-on-mismatch, 5 s timeout, 6105 protocol) as `[UNK]/deferred`, not as "supported".
- Resolve IPL3 maintenance ownership given the upstream archive (Pitfall 5).

**Warning signs:**
Claim text "boots commercial games" with no CIC/seed statement; HLE sets registers with no source; no test covering 8 MiB-plus open-bus reads.

**Phase to address:** S2.

### Pitfall 10: Region / TV type / CIC inferred from the ROM header

**What goes wrong:**
The emulator picks NTSC/PAL/MPAL and CIC from the header country byte or a title database, then derives VI timing, AI rate, `osTvType` etc. from it.

**Evidence:**
n64brew: the destination code "is not read by any hardware and no known game reads it"; flashcarts, menus and emulators merely use it as a hint; homebrew sets 0x00 `[CR: ROM Header]`. PIF-ROM differs for PAL vs NTSC consoles and hardcodes region `[CR: PIF-NUS]`. The "clock rate" field is a legacy libultra constant and "not safe" for real-time speed `[CR]`. `[OD]`/DNA: "OS TV type and cartridge region are related but distinct".

**How to avoid:**
- TV type, region, CIC, RAM size are **machine-profile inputs**, never derived from content. If a UI helper suggests a profile from the header, it is advisory and the chosen profile is recorded in the output.
- Refuse (explicit `refused: profile-mismatch`) rather than silently adapt; refusal leaves state unchanged `[OD]`.
- Test: same ROM under two profiles must differ only where the hardware says it does (VI timing, AI rate), and the test asserts the diff.

**Warning signs:**
`switch (header[0x3E])` anywhere in core; a `country` struct field in the machine config; PAL timing "automatically" selected.

**Phase to address:** S1/S2 (profile definition), S4/S5 (timing consumers).

### Pitfall 11: CPU: 32-bit vs 64-bit semantics, and "spec" vs real VR4300 behavior

**What goes wrong:**
The core implements textbook MIPS III (or R4300i docs) and diverges from real silicon in places that tests and some games notice. Typical failures: registers kept as 32-bit with sign-extension lost; 64-bit ops allowed/forbidden in the wrong mode; 32-bit ops given non-canonical (non-sign-extended) inputs behaving "cleanly" instead of leaking upper bits.

**Evidence (community reference, rev 2.2 observations `[CR: n64brew VR4300 + MIPS III pages]`):**
- `sra/srav`: upper 32 bits of the source leak into the result (e.g., `sra` of 0x0123456789ABCDEF by 16 yields 0x00000000456789AB on hardware), in both 32- and 64-bit modes; unknown whether ever fixed.
- `mult` behaves as a 64×35-bit signed multiply (second operand sign-extended from bit 34); `div` as 32×35-bit; inputs that are not properly sign-extended produce leaked 64-bit state.
- In 64-bit mode `ADD/ADDI` require sign-extended operands; overflow exception when carries out of bits 30 and 31 differ, destination unmodified.
- `DMFC0/DMTC0` on registers expected to be 64-bit (EntryHi, BadVAddr) `[CR: nemu64-test README]`.
- Load-use interlock checks the next instruction's rs/rt fields imprecisely, affecting timing only.
- Early NUS-01/02/03 boards: possible incorrect results after `mul.s/mul.d/mult` with NaN/zero/infinity operands; PRId differs (0x10, 0x22) by revision `[CR]`.
- The n64brew MIPS III page itself contains copy errors (SRL described as "sign-extended", XORI/SLTI destination field wrong, FPU section marked TODO) `[CR: observed typos]`, so the wiki is not a spec (Pitfall 15).

**How to avoid:**
- Keep a register file of full 64-bit values from day one; implement 32-bit semantics as defined operations on that file, not as a 32-bit subset.
- Make "console revision" a profile field (PRId, FCR0, mul bug presence). The first profile names one revision; the mul bug is explicitly out of scope until promoted `[REC]`.
- Native component tests with independent expected values for every instruction, including non-sign-extended inputs to 32-bit ops (generate from the NEC manual semantics and from nemu64-test vectors where hardware-derived).
- Run nemu64-test CPU/COP0/64-bit groups as required once pinned.

**Warning signs:**
`int32_t` register arrays; one `sign_ext(x)` helper called after every op; no test supplies non-canonical operands; PRId is a constant with no revision note.

**Phase to address:** S1.

### Pitfall 12: Delay slots, branch-likely, and exceptions around them

**What goes wrong:**
Branch-likely nullification, branch-in-delay-slot, exceptions taken in delay slots, and ERET (no delay slot) are implemented from memory. Symptoms are wrong EPC, wrong `Cause.BD`, wrong resume address, or double-executed/skipped instructions after TLB refill and interrupts.

**Evidence/expectations:** Branch-likely variants discard the delay slot when the branch is not taken `[CR]`. n64brew's MIPS pages do not describe delay-slot exceptions `[CR: observed gap]`. For MIPS III architecture: an exception in a delay slot reports EPC = address of the *branch* and sets Cause.BD; ERET returns to EPC with no delay slot; interrupts pending while in a delay slot are taken after the pair, etc. `[INF: architectural knowledge, not re-verified here against the VR4300 manual]`.

**How to avoid:**
- Model the pipeline-visible state explicitly: `pc`, `next_pc`, `in_delay_slot`, `branch_taken`, with the exception path reading these instead of reconstructing.
- Table-driven tests: each branch/branch-likely × taken/not-taken × (exception in slot: overflow, address error, TLB miss, interrupt, syscall/break, trap) × resulting EPC/BD/vector. nemu64-test lists exceptions (overflow, unaligned, TRAP, BREAK, SYSCALL) and TLB groups `[CR]`; add own native tests with independent expected values.
- Define behavior for a branch in a delay slot (architecturally undefined on MIPS): pick one, document it, and mark it `[UNK]` in the claim.

**Warning signs:**
An exception handler that decrements EPC by 4 conditionally; tests only ever run straight-line code; ERET implemented by "pc = EPC; pc += 4" patterns.

**Phase to address:** S1.

### Pitfall 13: Timing model by clock ratio only; COUNT/COMPARE/Random

**What goes wrong:**
The scheduler is "CPU 93.75 MHz, RCP 62.5 MHz, tick both". Count/Compare interrupts, Random register decrement, DMA durations and VI/AI cadence are then approximate in ways that either break tests or give a false sense of "cycle accuracy".

**Evidence:**
- The SDK documents Count as incrementing at half the CPU clock (46.875 MHz); the timer interrupt is raised by the CPU itself (IP7), and writing Compare clears the timer interrupt `[CR: SDK docs via ultra64.ca / web search; N64 core commit logs]`. Exact pipeline-clock relationship is `[UNK]` here.
- nemu64-test describes tiers: `timing` ("a NOP is 0.5 cycles, Random decrements by 1 per instruction"), `cycle` (parts of an instruction complete in later cycles), `cop0hazard` `[IO]`. The authors doubt `cycle` rules are fully derived and not dynarec-friendly.
- cen64's README stated an RTL-level accuracy goal with speed hopes (Pitfall 20).
- DNA: "Do not turn a clock rate into an adequate scheduler design" `[OD]`.

**How to avoid:**
- Declare a **timing tier per profile** (`T0 functional-ordering`, `T1 instruction-count with documented per-class costs`, `T2 cycle-accurate pipeline`). Claims cite the tier. First profile: T1 `[REC]`, with `timing` group advisory.
- Scheduler in integer guest ticks with a single master timebase; devices schedule events; no floating-point or host time.
- Tests: Compare-write-clears-interrupt, Count at half rate, Random decrement and wired behavior, expressed as exact tick expectations at the declared tier.

**Warning signs:**
Float timestamps; per-device "cycles per frame" constants unconnected to a master clock; "we are cycle accurate" with no tier definition.

**Phase to address:** S1/S2 (scheduler), S4/S5 (VI/AI).

### Pitfall 14: TLB, exceptions vectors, caches and uncommon CP0 detail

**What goes wrong:**
Several lumped subtleties are skipped because the first test ROMs don't need them: TLB refill vs invalid vs modified; XTLB refill in 64-bit mode; dual-page entries, global bit, ASID, PageMask, Wired; BadVAddr/Context/XContext updates; cache operations; CP0 writable-bit masks; reserved instructions and coprocessor-unusable.

**Evidence/status:** nemu64-test covers TLB and COP0 registers (64-bit EntryHi/BadVAddr) `[CR]`. The specific vector addresses, Status/Config writable masks, CACHE op semantics and "unusable" behavior were **not verified from a source in this research pass** `[UNK: verify against NEC VR4300 User's Manual]`. Architectural expectations `[INF]`: TLB refill uses a separate vector when EXL=0 (XTLB in 64-bit addressing), while TLB-invalid and TLB-modified use the general vector; CP0 registers have read-only/zero-forced bits whose write masks games and tests observe; coprocessor-unusable depends on Status.CU bits; Compare/Count/Status.IM/IP7 interplay.

**How to avoid:**
- Decide "caches as needed" `[OD: PROJECT.md]` into a written rule: the first profile either (a) models I/D cache state (needed for DMA-coherency tests and CACHE ops) or (b) explicitly states "coherent-memory model, CACHE ops are semantics-preserving no-ops where documented" with tests for which behaviors are in/out. Never leave it implicit.
- CP0: table of every register with writable mask, reset value, 32/64-bit width, per-revision differences; each row has a test of "write all-ones, read back".
- Exception vector table derived from the manual with a native test per exception class.

**Warning signs:**
`cp0[reg] = value` with no mask; `case CACHE: break;`; TLB implemented only for the single-entry lookups games use.

**Phase to address:** S1 (explicit scope decision at S1 start; promoted behaviors later).

### Pitfall 15: Treating n64brew and test-suite READMEs as specification

**What goes wrong:**
Wiki text is implemented as written, but it has typos, TODOs and self-flagged unknowns; test suites also have approximations suggested for bring-up that are explicitly wrong.

**Evidence (all observed 2026-11-09):** RSP CPU Core page: LRV pseudo-code uses `end & ~16` (probably `~15`), SWV/SSV opcode overlap, LTV/STV both at 0x0B, "(?)" opcodes, and no VMULF rounding or VRCP/VRSQ table text; SP DMA page: RDLEN bit-range inconsistent, a mislabeled header, SSTEP "unreliable", IO_BUSY "TODO: verify"; MIPS III page: SRL described as sign-extending, FPU section TODO; VI page: errata not fully explained. nemu64-test README suggests "Make LL work like LW; SC like SW; DMFC0 like MFC0" and states "the things above are wrong" but allow bring-up to proceed `[CR]`.

**How to avoid:**
- Every behavior requirement cites a *tier*: vendor doc (Nintendo manual via mirror) > hardware-derived test vector > self-checking ROM > wiki prose. Wiki-only claims are `[CR]` and need a test before they become a requirement `[OD: dated research must be independently checked]`.
- Bring-up shims are tagged `// BRINGUP-WRONG` and a CI grep fails release builds that contain them.

**Warning signs:**
Requirement text copied from n64brew verbatim; no test ID per requirement; `TODO: LL as LW` still present after the test group landed.

**Phase to address:** S0 (requirement-citation rule), S1/S3 (shim hygiene).

### Pitfall 16: RSP vector unit and memory semantics

**What goes wrong:**
Opcode coverage is mistaken for compatibility; arithmetic edge cases (clamping, rounding, accumulator slicing, reciprocal tables) and memory/DMA semantics are wrong in ways that only microcode stress reveals. A host-SIMD fast path then diverges from scalar semantics.

**Evidence `[CR: n64brew RSP CPU_Core, Interface, CPU_Pipeline; nemu64-test Cargo.toml]`:**
- Accumulator is 48 bits per lane, read as signed 48-bit; VSAR slices LO/MD/HI. Signed clamp saturates to int16; **unsigned clamp is asymmetric** (negative → 0, > 32767 → 65535, 32768-65535 passes through).
- The page gives no VMULF/VMACF rounding offset, no VRCP/VRSQ reciprocal-table/DIV_IN/DIV_OUT description, and no VCO/VCC/VCE flag semantics, so these must come from tests (nemu64-test has `vmulf/vmulu/vmulq/vmudl/vmudh/vmudm/vmudn/vmacf/...` stress features and `vrcp32/vrsq32_stress_test`, `rcp_rsq_dump`) `[IO]`.
- VMOV has a hardware bug where upper bits of the source lane come from `vd_elem`; LLV/LDV loads truncate at vector end but SLV/SDV stores wrap; MFC2/MTC2 `e=15` byte special cases; LQV/LRV pseudo-code is unreliable.
- SU: no exceptions, no likely-branches, 12-bit PC wraps at 0xFFC, DMEM address masked to 12 bits, misaligned scalar loads/stores must work.
- SP DMA: addresses/lengths 8-byte granular, length = N-1 rounded up to 8 (0..7 → 8 bytes), RDLEN reads 0xFF8 after completion, linear vs strided, stride applies only to RDRAM, transfers cannot span DMEM/IMEM, wrap within the bank, double-buffered queue with DMA_BUSY/DMA_FULL, HALT does not stop DMA.
- SP_SEMAPHORE: read returns old bit and sets it; release by writing 0.
- CPU access to DMEM/IMEM while the RSP runs has no arbiter; data is corrupted and, during a DMA, the DMA address is overwritten `[CR]`. SP_STATUS uses separate SET/CLR bits; setting both leaves the flag unchanged; BROKE sticky after BREAK; INTBREAK raises MI interrupt; SP_PC reads while running are random.
- Pipeline timing: 4-cycle VU result latency, dual-issue rules, a false dependency in single-lane ops (`vrcp $v01.e4` looks like `$v04`) `[CR: CPU_Pipeline]`: only needed at timing tier T2.

**How to avoid:**
- Implement a scalar reference RSP first; SIMD/JIT later must be differential-tested against it with random + edge-value + the nemu64-test stress vectors (run stress in a scheduled lane).
- Treat VRCP/VRSQ tables as *derived data with a test*, not copied constants (Pitfall 1).
- Decide and document CPU-vs-RSP DMEM overlap policy: "CPU access while RSP running" is either modeled (corruption) or declared `[UNK/deferred]`; do not silently serialize.
- Keep HLE/LLE decision explicit: opcode tests ≠ task compatibility `[OD: DNA]`. The first RSP milestone claims "ROM-level RSP tests" only `[OD: PROJECT.md]`.

**Warning signs:**
Rounding implemented as `(a*b + 0x4000) >> 15` from memory without a test source; `__m128i` intrinsics appearing before a scalar reference exists; reciprocal tables pasted from another emulator.

**Phase to address:** S3.

### Pitfall 17: RDP/VI: fixed 320x240, sequential frame loops, sync/readback races, deferred writes

**What goes wrong:**
Framebuffer output is assumed to be 320×240 RGBA with the RDP rendering "after the CPU finishes the frame". The VI is treated as a copy-out. Real behavior depends on VI registers, interrupt timing, shared RDRAM and RDP sync.

**Evidence `[CR: n64brew Video_Interface, RDP Pipeline/Commands; parallel-rdp README]`:**
- VI: output size depends on H/V window, X/Y scale, WIDTH and interlace; NTSC supports up to 480 lines hi-res interlace with alternating V_START/V_END per field, two origins and doubled WIDTH ("emulators hide this because they treat framebuffer memory as one contiguous block"); VI_V_INTR/V_CURRENT semantics with field bit (odd-field interrupt can fire a line early when V_INTR bit0=0 in interlaced mode); H_TOTAL/LEAP differ by NTSC/PAL/MPAL; mid-frame register change rules (ORIGIN/WIDTH/X_SCALE/Y_SCALE allowed in hblank, V_VIDEO latched); errata (REPLICATE + 16-bit + X_SCALE ≤ 0x200 + H_START<128 yields garbage; large X/Y_SCALE glitches); dedither only with REPLICATE or AA_ALWAYS; VI_ORIGIN may change during hblank with running offset preserved.
- RDP: syncs are not interlocked; unsynced attribute changes corrupt trailing pixels of the previous primitive (many cases still "TBC"); color/depth writes go through span buffers and flush later, fill-mode writes bypass them; Sync Full (0x29) raises the DP interrupt in MI and must be the last command before DP_END; sending commands via DP_START/DP_END while one is in progress can hang.
- parallel-rdp: "accurate emulation usually waits for the full sync ... many games tolerate syncing a few frames later"; RDRAM is shared with the CPU so GPU implementations need full coherency; the project lists unmodeled effects that need cycle accuracy.
- CPU/RCP overlap: `[OD: DNA]` "a CPU-then-GPU frame loop may hide races/order".

**How to avoid:**
- Core output is raw VI scanout (width, height, field, pixel format, line timing metadata), not a host-sized bitmap. Host scaling/filtering lives outside the core `[OD]`.
- RDP is a scheduled device: its display-list consumption and completion interrupt are events on the master timebase. Provide a "synchronous completion" policy as an explicit named mode and mark claims made under it.
- Test fixtures that read RDRAM during RDP work, change VI regs mid-frame, and interlaced hi-res (PeterLemon video tests and nemu64-test RDP groups only after per-case review; `experimental_rdp` stays research lane).
- Choose the RDP strategy explicitly: a deterministic **software reference RDP** is canonical; a GPU backend, if added, must prove bit-equality to the reference on a corpus and is presentation-only.
- Pick deterministic values for undefined cases (noise seed, undefined MemoryColor with image_read off, 9-bit hidden coverage in RDRAM) and list them as named "policy choices", like parallel-rdp does.

**Warning signs:**
`const int WIDTH = 320`; frame loop "run CPU for N cycles, then RDP, then present"; VI_V_CURRENT derived from a host vsync; no test using hi-res interlace or PAL.

**Phase to address:** S4 (design before code); revisit at S2 scheduler.

### Pitfall 18: Audio tied to the host clock; AI DMA treated as a host buffer queue

**What goes wrong:**
Host audio callbacks pull from the emulator, so guest AI cadence follows the host audio clock (non-determinism, dropped or stretched samples). Or the AI is modeled as a ring buffer without DMA address/length/interrupt semantics.

**Evidence `[CR: n64brew Audio_Interface]`:** the AI has no sample RAM; DMA feeds the DAC at `VI_clock / (DACRATE+1)` (example 44,136 Hz NTSC; PAL values not listed `[UNK]`); the interrupt fires when a DMA **starts** (so the CPU can queue the next buffer), acknowledged by AI_STATUS access; FULL/BUSY bits and double-buffering; AI_LENGTH reads return bytes remaining; **hardware bug: if a transfer ends exactly on an 8 KiB boundary the next buffer's address gets +0x2000** (libdragon has a workaround); DRAM_ADDR is write-only and reads mirror LENGTH. SDK advises audio-task priority when graphics overrun deadlines `[OD: DNA]`.

**How to avoid:**
- Core emits raw PCM with guest-time stamps (guest sample index + DACRATE) into a bounded buffer; the host resamples/plays and never feeds back into guest time. Underrun/overrun are host concerns, visible in telemetry, not guest state.
- Model AI DMA start/finish events on the master timebase, including double-buffering and the 8 KiB-boundary quirk (profile-togglable if proven revision-dependent `[UNK]`).
- Audio oracle: authored diagnostic with exact expected samples per DMA buffer; "non-silent" never counts (Pitfall 2).

**Warning signs:**
SDL audio callback calling `run_frame`; `sleep()` for pacing in core; PAL and NTSC sharing a single DACRATE constant.

**Phase to address:** S5.

### Pitfall 19: Save media guessed from titles; SI/Joybus modeled as byte arrays

**What goes wrong:**
Save type is inferred from the game title or a bundled DB, and saves are one flat byte array. EEPROM, SRAM and FlashRAM have different buses and protocols; Controller Pak has CRC/checksum/state rules; RTC writes are ignored in favor of host time.

**Evidence `[CR: n64brew Joybus_Protocol; SaveTest-N64 via search]`:**
- EEPROM is on the SI/Joybus: info response 0x0080 = 4 Kbit (blocks 0-63, higher blocks mirror), 0x00C0 = 16 Kbit; writes are 8-byte blocks with a ~6 ms background write and a busy status (0x80) that real software observes; unsupported commands time out (no reply).
- SRAM and FlashRAM are cartridge/PI Domain 2 devices that cannot coexist (same address space); FlashRAM has a command protocol and device IDs `[UNK: not verified here]`; SRAM 768 Kbit exists (e.g., one banked case); detection of EEPROM+SRAM combos is theoretically possible but unsupported by tools. Flash-cart tooling notes non-EEPROM saves need 32-bit endian swap when changing platforms `[CR: 64drive docs via search]`.
- Controller Pak: 32-byte blocks, 11-bit address + 5-bit address checksum (invalid → Pak acts absent), CRC-8 (poly 0x85) over data, absent Pak returns zeros with complemented CRC (0xFF), "newly inserted" status 3 returned once, reads/writes blocked until Info shows status 3 `[CR]`. A corrupted write still goes through and the CRC reply reveals it.
- Joybus timing: ~62.5 µs response window, 4 µs bit cells `[CR]`.

**How to avoid:**
- Save device is a **profile/content-admission choice**, explicit in the API (`save=eeprom16k | sram256k | flash1m | none`), never guessed from title. Unknown → refuse or run without saves per policy; refusal leaves state unchanged `[OD]`.
- Host owns durable storage; the core exposes the device image and dirty/commit semantics. Core never opens save files `[OD]`.
- Tests: write-in-progress busy window, 4K mirror wrap, refused-op postconditions (bad block, bad CRC/checksum, absent pak), import/export round trip including endianness, size mismatch refusal.
- RTC (if ever in scope): base time is a profile/input parameter, writes honored.

**Warning signs:**
`if (title.contains("Zelda")) save = FLASH`; one `uint8_t save[0x20000]`; EEPROM writes complete instantly; Controller Pak accepted without checksum validation.

**Phase to address:** S6 (save baseline first: EEPROM 4/16K, SRAM; Flash later `[OD: PROJECT.md]`).

### Pitfall 20: Process: premature JIT/optimization, plugin sprawl, per-game hacks, scope creep, abandonment

**What goes wrong:**
Speed work, plugin APIs or compatibility hacks arrive before a correctness baseline, producing an unmaintainable system; scope grows to 64DD/accessories/enhancements; the single maintainer burns out.

**Evidence:**
- cen64: BSD-3 `[PF]`, created 2013; its README frames it as a "pet project ... I pick up whenever I get bored" aiming at RTL-level "perfect" emulation *and* eventual full speed `[IO: README]`. Commits in 2022 and 2023, then build-fix merges in Oct 2025 from outside contributors `[IO]`; secondhand wiki says the author "appears to have abandoned the project citing lack of satisfaction with his stated goal of fast cycle-accurate emulation" `[CR: GameTech wiki via search; unconfirmed, no primary statement found]`. Lessons `[INF]`: a single maintainer, unfunded; a conflicting accuracy-vs-speed goal; no staged correctness tiers; bus factor 1; build rot after ~2 years of low activity.
- ares v148 (2026-05-30) *rewrote* its N64 CPU/RSP JIT; JIT is a multi-iteration, tier-two investment even for a mature project `[OD: DNA, observed release]`.
- Mupen64Plus/Project64 plugin splits are historical reference only; `[OD]` out of scope.

**How to avoid:**
- Performance work is gated by a named correctness baseline and a benchmark manifest; interpreter first, then a cached interpreter, then (maybe) JIT with differential tests against the interpreter on every instruction class and on test ROMs. JIT is S8, not S1 `[OD/REC]`.
- One canonical core, no plugin ABI. A single narrow core API frozen only after lifetime/profile/content/time/output/failure rules are tested through the installed consumer `[OD]`.
- Quirk policy: no title/CRC-keyed hacks in core. Behavior differences must be keyed to named hardware features/profiles with evidence; any compatibility shim lives in a host-side "profile preset" that is clearly labeled and cannot affect the evidence tier.
- Scope guard: 64DD, Transfer Pak, widescreen, upscaling, netplay, cheats are listed in a deferred table with promotion criteria. Add the "playable rights-cleared homebrew path" so the project isn't tests-only `[OD]`.
- Keep milestone deliverables small and releasable (autonomy workflow); record lessons every milestone.

**Warning signs:**
Code-generation work before RSP/CPU conformance; `#ifdef GAME_xxx`; a plugin interface header; "just add Transfer Pak quickly"; no release in two milestones.

**Phase to address:** S0 (policy), S7 (API freeze rules), S8 (performance), S9 (promotion criteria).

## Moderate Pitfalls

### Pitfall 21: Unaligned access and LL/SC details
**What goes wrong:** LWL/LWR/LDL/LDR/SWL/SWR/SDL/SDR merge wrong for byte offsets, wrong sign extension of LWL/LWR results in 64-bit mode, or address-error exceptions raised/not raised wrongly for LW/LH/LD at misaligned addresses (nemu64-test covers unaligned LW exceptions and LL/LLD/SC/SCD `[CR]`). LL/SC: LLAddr register, link-bit clearing on ERET/exceptions, SC fail behavior, SCD mode restriction `[INF: not re-verified]`. n64brew MIPS III page gives no alignment rules `[CR: observed gap]`.
**Prevention:** Table-driven tests for every access width × alignment × endianness × 32/64-bit mode × segment (KSEG0/1/USEG-mapped) with independent expected values; resist "LL as LW" shims beyond bring-up (Pitfall 15).
**Warning signs:** Only aligned tests; one shared load helper for all widths. **Phase:** S1.

### Pitfall 22: FPU rounding, denormals, NaN and unimplemented-operation exceptions
**What goes wrong:** Host FPU is used directly; rounding modes (FCR31), flush-to-zero/denormal handling, NaN payloads, conversion overflow (CVT, TRUNC, ROUND with out-of-range), compare/branch condition codes and Cause/Enable/Flag bit sequencing differ from the VR4300; the VR4300 raises *Unimplemented Operation* for cases it won't handle in hardware, which software traps. The FPU page on n64brew is TODO `[CR: observed]`, so expected values come from the manual or hardware vectors `[UNK: not verified here]`. nemu64-test has `cop1_stress_test` and COP1 tests `[IO]`. Early boards have a mul bug (Pitfall 11).
**Prevention:** Software float (softfloat-style) or host-FPU with fenced modes and verification; every FPU op × rounding mode × special inputs table; Cause-bit tests; decide revision (mul bug) per profile. **Warning signs:** `(float)` casts in the interpreter; no tests of denormal inputs; FCR31 as a plain integer. **Phase:** S1 (FPU subphase; stress test in scheduled lane).

### Pitfall 23: PI DMA and open-bus semantics
**What goes wrong:** PI DMA modeled as `memcpy` with ideal alignment, ignoring first-block misalignment behavior, 128-byte blocks within 2 KiB RDRAM pages, odd-length extra byte, PI_WR_LEN readback (0x7F), domain-1/domain-2 timing registers, open-bus return values, and confusion between PI bus addresses and CPU physical addresses `[CR: n64brew Peripheral_Interface]`. RDRAM reads above mapped chips return zero, no mirroring `[CR: nemu64-test README]`; behavior between 4 MiB and 8 MiB when no Expansion Pak is `[UNK]`.
**Prevention:** A PI model with named quirks; use the hardware-dump-based `n64_pi_dma_test` repo suggested by n64brew only after verifying existence, license and provenance `[UNK: not checked]`. **Warning signs:** DMA completes in zero guest time; unmapped reads return 0xFF or 0; cart address wraps assumed. **Phase:** S2.

### Pitfall 24: Interrupt/MI ordering, masked vs pending, and status acknowledge semantics
**What goes wrong:** Interrupt lines (SP, SI, AI, VI, PI, DP) are simulated as events with no pending/mask distinction. n64brew's DP note: a masked interrupt is still recorded in MI_INTERRUPT; enabling the mask while pending signals immediately `[CR]`; VI interrupt cleared by writing VI_V_CURRENT; AI by AI_STATUS; SP by CLR_INTR; PI by writing bit 1 of PI_STATUS.
**Prevention:** One MI model with per-source ack rules and tests of "pending while masked → unmask → immediate" for every source. **Phase:** S2.

### Pitfall 25: Test harness results protocol and ISViewer capture
**What goes wrong:** Mirroring text to ISViewer registers is implemented partially: buffer at `0xB3FF0020..0xB3FF0220`, length register `0xB3FF0014` `[CR: nemu64-test README]`; truncated lines, host-side buffering on process kill, unbounded output, non-UTF8 or control characters corrupting logs, and the runner stopping at first "Done!" line while later output indicates failures.
**Prevention:** Bounded capture buffers; structured result parser with a strict grammar and a version tag; the runner records raw capture as an artifact. Treat the on-screen console as supplementary. **Phase:** S0.

### Pitfall 26: Playable-path gap (tests-only trap) and demand claims
**What goes wrong:** All effort goes into passing diagnostics while no rights-cleared playable title exists, and prior claims of demand (Switch Online study) are repeated as if proven `[OD]`.
**Prevention:** S2-S4 target a small authored or rights-reviewed homebrew demo as an acceptance fixture; claim tables list only evidenced rows. **Phase:** S4/S7 milestone gating.

### Pitfall 27: Dependency and supply-chain creep through test tooling
**What goes wrong:** Adding a language toolchain (Rust nightly + nust64 + `cargo`) just to build a test ROM pulls many crates. nemu64-test depends on `linked_list_allocator`, `spinning_top`, `arrayref`, `oorandom`, `arbitrary-int`, `bitbybit`, `num-traits` `[IO: Cargo.toml]`; the build needs `nust64` and a pinned toolchain.
**Prevention:** Keep fixture *build* in an isolated, pinned lane distinct from emulator build; prefer prebuilt-by-digest where rights allow, and keep the emulator's own dependency tree free of fixture-toolchain deps `[OD: small flat tree]`. **Phase:** S0.

### Pitfall 28: Public CI with commercial ROMs, saves, or firmware
**What goes wrong:** A "private" test path using commercial ROMs leaks into public CI logs/artifacts, or a ROM hash list is used as if hash = license.
**Prevention:** Public CI uses only manifest-cleared fixtures; commercial content is local-only on the owner's machine with no CI upload; logs from local runs don't include frames or save dumps. `[OD]` "A hash proves identity, not rights." **Phase:** S0.

### Pitfall 29: Serialization/save-state and refused-operation postconditions
**What goes wrong:** Content admission failures (bad size, byte order, truncated ROM, malformed save) partially mutate the instance; parsers read unbounded sizes. `[OD: Security]` requires bounded parsers and unchanged state on refusal.
**Prevention:** Admission is a pure validate-then-commit; fuzz the ROM/save admission paths; test "state digest before == after" for every refusal. Byte order (z64/v64/n64) detection should be explicit input or strict validation, and n64brew treats non-big-endian layouts as obsolete `[CR: ROM Header]`. **Phase:** S7 (core API), with admission code beginning at S2.

## Minor Pitfalls

### Pitfall 30: ROM header "check code" treated as CRC or content authentication
**What goes wrong:** The header 8-byte check is not a CRC and is not authentication `[CR: ROM Header]`; it is only an IPL3 boot gate (and not even required by libdragon's IPL3). **Prevention:** Use it only for "will Nintendo IPL3 accept this" diagnostics, not identity. **Phase:** S2.

### Pitfall 31: Clock-rate header field used for time
**What goes wrong:** Header offset 0x04 (clock rate) is legacy libultra input; not safe for real-time speed `[CR]`. **Prevention:** Ignore for scheduling. **Phase:** S2.

### Pitfall 32: VI filtering/gamma/divot/dither folded into host scaling
**What goes wrong:** VI-stage effects (AA modes, divot, dedither, gamma, gamma dither) are skipped or merged into a host upscaler, then raw-output hashes can't be compared. **Prevention:** Model VI effects in the core raw path with a flag to bypass; host scaling only afterward `[OD]`. **Phase:** S4.

### Pitfall 33: Trademark/name assumptions
**What goes wrong:** "Tendies64" is not trademark-cleared `[OD]`. **Prevention:** No store listings or logo/branding claims before clearance; repo metadata states working name. **Phase:** S7/S9 pre-release.

### Pitfall 34: Endianness of fixture and save files
**What goes wrong:** Flash-cart/emulator ecosystems disagree on byte-swapping of save files `[CR: 64drive docs via search]`. **Prevention:** Declare canonical on-disk format and conversion in the content-admission contract; test a swap round trip. **Phase:** S6.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Instruction-at-a-time CPU with 1-cycle-per-instruction and no cache model | Fast bring-up | Timing/cache tests unreachable; claims limited to T0/T1 | Acceptable if profile states tier and test groups are scoped accordingly |
| LL as LW, SC as SW, DMFC0 as MFC0 (nemu64-test suggestion) | Lets suite reach the end | Hides real failures; false green | Bring-up only; tagged and release-blocked |
| Host float for FPU | Simple | Non-deterministic across hosts; wrong denormals | Never in canonical core |
| SIMD RSP before scalar reference | Speed | Unverifiable divergence; cross-host drift | Never |
| Copy expected output from another emulator | Instant "green" | Inherited bugs, rights questions (Angrylion) | Only as labeled `differential` rows |
| RDRAM zero-filled at power-on | Easy | Hides uninitialized-memory dependency; differs between IPL3s | Acceptable as a named profile field, documented |
| Title-keyed DB for save type | Games "just work" | Wrong media, silent data loss | Never in core; host-side advisory only |
| Single-thread-then-add-threads for RDP | Fast | Race conditions become nondeterminism | Only if threading is deterministic by construction (frame-barriered) and differential-tested |
| Commit prebuilt test ROMs | Simple CI | Rights/provenance leakage | Never unless rights are cleared per asset |
| Wiki prose as requirement | Quick | Typos/unknowns baked in | Never without a test |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Per-instruction scheduler checks | Slow interpreter | Event-driven scheduling with next-event horizons | When running commercial-sized workloads; measure first |
| Software RDP per-pixel with branches | Frames take seconds | Deterministic span-based software RDP, then optional GPU presentation backend | Hi-res/AA/2-cycle workloads |
| Full-state hashing every tick in determinism tests | CI timeouts | Hash at fixed guest times/checkpoints | Long test ROMs |
| Mirror `memcpy` for DMA | Fast but wrong | Model quirks, then optimize behind tests | Any PI/SP DMA conformance |
| JIT too early | Instability, untestable | Interpreter correctness baseline, differential JIT | `[OD]` correctness first |
| Conflating CI time and emulation throughput | Misguided optimization | Report emulation throughput, latency, resource use, CI time separately `[OD]` | Any perf review |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Unbounded ROM/save/archive sizes | Memory exhaustion, crashes | Size caps, early reject; fuzz admission `[OD]` |
| Partial state mutation on refusal | Corrupt instance, exploitable states | Validate then commit; state-digest equality tests |
| Guest-controlled DMA lengths/addresses indexing host buffers | Out-of-bounds host reads/writes | Mask to modeled address spaces; bounds-checked device models; fuzz DMA registers |
| JIT/dynarec W^X mistakes later | Code-injection surface | Defer JIT; if added, isolate and fuzz |
| Archive parsers (zip/7z) for ROM intake | Parser CVEs | Host-side only, not in core; or no archive support in baseline |
| Fixture download scripts executing fetched code | Supply-chain attack | Pin by digest; no `curl | sh`; isolated build lane |
| Save/ROM paths in logs | Privacy/rights leak | Redact paths; no content frames in public artifacts |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|
| Silent profile auto-selection from header | Wrong TV/CIC, confusing bugs | Explicit profile chosen/recorded; advisory suggestions only |
| Refusal without reason | Developers can't script around it | Machine-readable refusal codes + unchanged-state guarantee |
| "Passed" message for timeouts | False confidence | Six-way outcome enum; nonzero exit for anything but pass |
| Host-paced audio glitches blamed on the emulator | Mis-diagnosis | Separate guest audio correctness from host playback telemetry |
| Claims in README implying broad compatibility | Trust loss | Claim table bound to profile/evidence tier/build ID |

## "Looks Done But Isn't" Checklist

- [ ] **Headless runner:** often missing empty-output/timeout/missing-fixture classification. Verify all four negative controls fail correctly.
- [ ] **nemu64-test pass:** often missing total-count pin and feature-set record. Verify the manifest pins `N` and flags.
- [ ] **CPU:** often missing delay-slot exceptions, non-canonical 32-bit operands, CP0 masks, unaligned/LL-SC. Verify native tests exist for each.
- [ ] **FPU:** often missing denormal/unimplemented-operation and rounding-mode coverage. Verify against stress vectors.
- [ ] **RSP:** often missing unsigned-clamp asymmetry, VMOV bug, DMA wrap/queue and SU wrap. Verify the stress groups pass in the scheduled lane.
- [ ] **VI:** often missing hi-res interlace, PAL/MPAL, mid-frame register changes, field bit. Verify a fixture per mode.
- [ ] **RDP:** often missing sync-full timing and unsynced-attribute behavior. Verify the Sync Full interrupt and named policy choices.
- [ ] **Audio:** often missing AI start-interrupt semantics and 8 KiB boundary quirk. Verify an authored diagnostic with exact samples.
- [ ] **Boot:** often missing documented unmodeled PIF behaviors and CIC variant statements. Verify the boot-limits doc exists.
- [ ] **Saves:** often missing EEPROM busy window, 4K mirroring, refused-op preservation. Verify tests for each.
- [ ] **Controller Pak:** often missing checksum/CRC/status-3 rules. Verify absent-pak behavior (zeros, CRC 0xFF).
- [ ] **Determinism:** often missing cross-host and sanitizer runs. Verify the same digest on two OSes and with ASLR varied.
- [ ] **Rights:** often missing per-asset audit. Verify every fixture manifest entry includes asset and tool-blob rights.
- [ ] **Independent installed consumer:** often missing teardown/refusal postcondition tests. Verify against a clean installed package `[OD]`.

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Wrong oracle (emulator-derived expectations) | MEDIUM | Re-label expectations by provenance, demote claims, re-derive from self-checking ROMs |
| License contamination | HIGH | Quarantine files, clean-room rewrite from specs/tests, or adopt compatible license by owner decision; audit git history |
| Embedded asset rights issue in a fixture | LOW-MEDIUM | Remove binary, switch to build-on-demand or replace with owned asset; rewrite manifest |
| Non-deterministic core | HIGH | Add state-digest bisect harness, find leaks by differential runs under varied env; remove host dependencies |
| Premature JIT entrenched | HIGH | Freeze JIT, maintain interpreter as reference, differential harness, remove per-game hacks |
| Frozen API that doesn't fit | HIGH | Version API; independent consumer test to detect; avoid freezing before S7 |
| Upstream fixture/IPL3 disappears (libdragon archive) | MEDIUM | Use pinned SHA mirror (license-permitting), assign maintenance owner, rebuild from source |
| Wrong save-type handling and corrupted user saves | MEDIUM | Version save format, add refusal tests, document recovery/export tool |
| Tests passing on empty | LOW | Add negative controls, pin counts, re-run history |
