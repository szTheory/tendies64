## Design decisions recorded by this plan (routine, reversible until F2)

- **Where replay lives.** Record and play are runner-side and run inside the existing `run_real` advance loop (D-34: the core knows nothing of replays). Record keeps the real run authoritative: the t64.result of a record run is the ordinary result, the replay is an extra private artifact published only when the loop ended at `guest-completion` or `guest-bound`. Play re-runs the same fixture row with an empty `t64.input` schedule (a schedule with events is refused) and the replay supplies every input; the t64.result of a play run is the ordinary result. A mismatch before the guest starts is the existing prelaunch refusal (`refusal`, guest tick 0); a divergence or a driver refusal after the guest started is the existing `harness-error` with stop kind and detail `host-error`; the specific cause lives only in the `t64.replay-report` (no new t64.result key or detail value, K10).
- **Where the report goes.** A separate closed record `t64.replay-report` v1, published as a private single file through the 09-02 publisher (leaf extension `rpr`, not a denied extension because it holds digests, ticks and field names only, never in the upload allowlist). The replay itself uses extension `rpl` (denied by the 09-02 scanner row).
- **Submission modes.** The real runner pre-queues the whole script before the first advance, so its replays hold every input at `at` 0 in script order (D-03 scripted pre-queue). The in-process reference and driver additionally support just-in-time submission at completed-tick boundaries (lead 5,000 ticks before the event tick) so `at` greater than 0 is exercised and goldens exist for both modes. Digests of the two modes differ by design and the plan asserts that difference as a witness, never as a claim of equality.
- **Replay-mix timeline.** User code first retires near tick 538,800 (K3), so the ROM polls the controller six times with a measured delay loop between polls; the committed input script stamps each state in the gap between two measured poll execute ticks, with a margin assertion in a test, so the transcript depends on ordering only. The row uses `T64_REAL_GUEST_TICKS_LONG_CAP` (K3) and the record and play bound 1,500,000.
- **save_init.** `blank` or an image record (SHA-256 plus length); the live value is read from the machine through the 09-05 export after admission and any pre-run import. Replay flags are refused in combination with the runner save import and export options (undefined combination in v1), so the image form is exercised in process only (documented limit).
- **Caps.** Document at most 4,194,304 bytes, ops at most 65,536 including the end op, checkpoints at most 4,096. The op cap is not reachable at the default byte cap with input ops (a minimal canonical input op is about 75 bytes, so about 55,900 fit), therefore the parser takes an explicit limits struct and the cap refusals are exercised through lowered limits on the same code path, with the default constants asserted by value and the byte cap exercised at default.
