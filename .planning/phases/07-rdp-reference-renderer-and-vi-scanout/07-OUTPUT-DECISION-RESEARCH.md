## VI guest time and raw-frame backpressure

| Option | Pros | Cons | Complexity | Recommendation |
|--------|------|------|------------|----------------|
| Advance a rational VI-domain phase from canonical guest ticks; queue complete raw field/frame packets in a bounded FIFO | Keeps RDP/VI/CPU on one `(guest_tick, sequence)` order; exact remainder makes whole and split advances equivalent; lossless capture; preserves field identity and scanout metadata | Must choose a documented software clock mapping per TV mode; full queue can pause guest advancement; bounds and event-full boundary need explicit checks | VI phase/events, digest/state, bounded output storage and copy-out -- Risk: drift, overflow, and same-tick ordering if phase or capacity is mishandled | Rec if reproducible capture, split advances, and Phase 8 file capture are required |
| Advance rational VI phase but retain only the newest field/frame with sequence and sticky loss count | Bounded memory; guest execution need not wait for a slow live viewer; metadata can expose skipped output | Drops fields by design; cannot claim complete raw capture or reproduce a full output stream after loss | VI phase, one output slot, loss telemetry -- Risk: missed fields can be mistaken for complete capture | Rec if a later live-preview mode explicitly permits loss; not for the Phase 7/8 capture path |
| Treat each CPU instruction step/tick as a VI cycle and use a bounded FIFO | Reuses the CPU event boundary; avoids a separate conversion accumulator in a visual prototype | Current ticks are `model-rsp-cycle`, not pixels or VI cycles; CPU T1 costs vary by instruction, CPU may idle, and TV clocks differ; output cadence would track retirement rather than elapsed guest time | CPU/VI event coupling and output queue -- Risk: incorrect TV cadence, event-order changes, and host-visible output varying with guest instruction mix | Rec only for an explicitly synthetic, untimed mock; reject for a profile-timing claim |

**Rationale:** Use the canonical scheduler tick with a rational video-phase accumulator and retain its remainder in the machine's future-affecting VI state. Drive line/field boundaries from that phase, not CPU retirement; bind any selected NTSC/PAL/MPAL rate mapping to the existing profile policy and version only a concrete semantic change under [the approved CPU compatibility policy](../../../docs/spec/cpu-compatibility.md). Nintendo's [VI chapter](https://jrra.zone/n64/doc/pro-man/pro30/30-01.htm) describes signal timing, active display modes, interlace and VI filtering; the [RCP register header](https://ultra64.ca/files/documentation/online-manuals/man/header/rcp.htm) identifies separate VI clock constants plus current-line, active-window, scale, 16/32-bit source format and filter controls. These establish the separate video domain and disprove a fixed 320×240 assumption; the conversion from Tendies64's selected `model-rsp-cycle` tick, exact event costs, and register-write timing remain software policy or phase research, not established hardware behavior. For lossless output, let the core own a fixed-capacity queue of immutable `RGBA8` software-capture packets while the host owns its read cursor and files; record actual width/height, field/parity, source pixel depth, output encoding, VI filter flags, guest tick, sequence, profile and build. Keep host scaling/presentation out of the core; exclude output bytes and host cursor from the canonical digest, while including VI phase and pending VI events. Before dispatching a field event, reserve a whole packet slot; a full queue yields a resumable `output-full` stop at that scheduled boundary, leaving the VI event and its effects pending. Drains only copy bytes and advance the observer cursor; insufficient capacity reports the required size without copying or moving the cursor, and invalid spans leave both spans and cursor unchanged. Cheap pre-suite checks: compare independently calculated fill pixels at RDRAM and VI separately; prove a deliberately wrong expected VI pixel fails; compare whole versus partitioned advances with drains and require byte-identical packets/metadata and equal canonical digest at the same guest tick; fill the queue and verify same-boundary resume, no overwrite, and no guest-time advance from drain; exercise non-320×240 geometry, 16/32-bit source metadata, field parity and filter metadata. Reverse this choice only if sourced behavior plus authored split-advance probes show the current tick cannot represent required field boundaries with a bounded exact rational phase; then version only the affected timing semantics, without per-device/per-fix profiles or a stricter compatibility promise. This research did not run builds or tests, use ROMs/guests/protected assets, or consult oracles; D2, D5 (including its asset/authority gates), and D6 remain in force. No host clock, core file I/O, presentation path, or API/ABI freeze is implied.
