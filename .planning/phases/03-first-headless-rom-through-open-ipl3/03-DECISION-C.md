# Phase 3 Decision C — Runner and authored fixture

**Scope:** Headless runner/result seam, tiny hello fixture, deterministic input trace and fixture provenance. Agent A owns the IPL3/license/toolchain audit; Agent B owns hardware-manual facts and initial-boot contract. This note does not approve protected bytes or claim hardware fidelity.

## Recommendation

Use a repo-authored, minimal MIPS assembly hello payload built with a pinned N64 cross-toolchain; load the approved pinned IPL3 from Agent A as a separate boot input. Keep the fixture builder small: source assembly, linker script, and a deterministic ROM packer for only the header/layout/byte order required by the agreed loader contract. Do not bring in the full libdragon SDK, hand-encode MIPS instructions, or use nemu64-test. Record source, revision, exact recipe/toolchain, binary digest/size, expected log provenance, separate source/binary rights and permitted CI distribution in the existing manifest.

Add a real guest-runner identity and a strict `t64.result` schema version for guest execution if the required fields cannot fit v1 without weakening its closed-field/null rules. Update the consumer to read both v1 and the new version; preserve v1 bytes and goldens. Never convert `t64.model-result` into a guest result. Reuse the six outcome names and the established harness-error precedence, but give the authored hello its own exact expected transcript oracle: v1 explicitly calls its `PASS`/`FAIL`/`Done!` grammar synthetic-only. Keep the result’s machine-readable pass tied to a real CPU execution through the pinned IPL3 and to the captured guest output.

## Smallest fixture construction seam

Three paths were considered:

| Path | Tradeoff | Decision |
|---|---|---|
| Full libdragon SDK/application template | Useful for ordinary homebrew, but imports a broad runtime/build graph and obscures which code the first boot slice needs. It also does not remove the requirement to pin the boot artifact independently. | Do not use for this first fixture. Revisit if later fixture breadth needs SDK facilities. |
| Hand-encoded instruction words or a custom assembler | Minimal files, but makes the guest opaque and creates an unnecessary instruction-encoding tool to maintain. | Reject. |
| Tiny authored `.S` payload + linker script + narrow deterministic ROM packer, using pinned N64 binutils/compiler | Small and inspectable, with compiler-generated instructions and a documented final byte artifact. Packer is limited to cartridge container/header tasks, not a CPU assembler. | **Recommend.** Pin and verify every cross-tool used by local and CI builds. |

Use the pinned open IPL3 candidate Agent A is auditing (`n64brew/libdragon` revision `98154dafd5ac50e74ee09a5de1035d24a53f54f0`, `boot/`); its exact per-file rights and reproducible source-build/signing chain remain an Agent A checkpoint. Do not silently treat the prebuilt signed blob as a reproducible source build. It is acceptable to use a cleared tracked artifact as the phase baseline if its exact rights/provenance are documented; otherwise make the approved source-build/sign path part of the phase and CI. The current host has Apple Clang, CMake and Ninja but no `mips64-elf-gcc`, `mips64-elf-as` or `mips64-elf-ld`; no ROM build was possible locally. No package was installed or protected asset fetched.

Manifest/distribution follows the current rights policy: hashes establish identity, not rights; source and binary rights are separate; ROM bytes are committed/uploaded only when documented as authored-here or cleared and that channel is listed. If CI is not allowed to publish the ROM, build it inside the job and keep it out of uploaded artifacts. A CI matrix needs the same authorized fixture bytes on each leg, so either distribute that cleared artifact internally under the listed channel or build it from the same pinned recipe in every job and assert identical fixture digests.

## ISViewer compatibility contract

**Source facts.** Official libdragon docs identify `ISVIEWER_MAGIC` at `0x13FF0000`, `ISVIEWER_WRITE_POINTER` at `0x13FF0014`, `ISVIEWER_BUFFER` at `0x13FF0020`, and `ISVIEWER_BUFFER_LEN` as `0x200` ([libdragon debug reference](https://libdragon.dev/ref/debug_8c.html)). At archived upstream libdragon commit `e356bf3f56f7afbf7e5246329562f145965cfdfc`, `src/debug.c` tests the magic register; writes aligned, big-endian 32-bit words into the buffer in chunks up to 512 bytes; and writes the exact unpadded byte count to `ISVIEWER_WRITE_POINTER`. Its source comment says this reuses the pointer as a length register because emulators often do not update pointers, and says libdragon is not implementing the real circular-buffer access pattern ([pinned source, lines 81–139](https://raw.githubusercontent.com/DragonMinded/libdragon/e356bf3f56f7afbf7e5246329562f145965cfdfc/src/debug.c)).

At Ares revision `0b928930af4cc59ed99e942996f0d3c815379388`, `ares/n64/cartridge/isviewer.cpp` intercepts PI accesses in `0x13ff0000..0x13ffffff`; its halfword write handler flushes when the offset is `0x16`. Its comments distinguish libultra’s pointer interpretation from libdragon’s byte-count interpretation and explicitly say Ares assumes libdragon behavior. This is evidence of an emulator compatibility implementation, not hardware truth ([pinned Ares source](https://github.com/ares-emulator/ares/blob/0b928930af4cc59ed99e942996f0d3c815379388/ares/n64/cartridge/isviewer.cpp)).

**Software contract recommendation.** Model the narrow libdragon path only: magic presence check, buffer at `+0x20`, up to `0x200` bytes per write, big-endian word storage, and flush exactly the requested byte count including a final partial word but excluding padding. Preserve output as guest bytes. Treat a 32-bit count store addressed at `+0x14` and an emulator’s flush on the `+0x16` halfword lane as compatible observations; the lane relationship is an inference from word/halfword accesses and needs Agent B’s manual review before any hardware claim. Do not implement libultra pointer/ring semantics under this contract. Test magic detection, lengths 0/1/3/4/512/513, padding exclusion, chunk boundaries and repeated flushes.

## Timed logical input and trace boundary

The current scheduler orders same-tick events by sequence and emits the trace record at the event’s guest tick before its handler; trace is an observer queue ([`core/t64_scheduler.c`](../../../core/t64_scheduler.c), [`core/t64_trace.c`](../../../core/t64_trace.c)). The roadmap requires an input script and events at scheduled guest ticks; controller delivery over SI/PIF is a later SAVE-01 requirement ([`ROADMAP.md`](../../ROADMAP.md), [`REQUIREMENTS.md`](../../REQUIREMENTS.md)).

Accept a bounded, canonical logical-input schedule in the host runner and queue each event at its declared guest tick. Emit those records through the existing trace seam; include a canonical input-schedule digest in the real result so the run identity is replayable. At this phase, describe this accurately as timed input scheduling/trace: do not claim that a controller or the hello guest consumes the buttons before SI/PIF exists. Keep host timestamps and physical-device mapping out of guest time and core state. If the phase implements any input-latch state that affects the state digest, make it profile-bound and test it explicitly; otherwise input identity belongs in `input_digest` and trace, not in a claim that this ROM used a controller.

## Real-result and outcome seam

Current `t64.result` v1 is closed to unknown fields, stamps `synthetic-stub`, sets `state_digest` null and calls its PASS grammar synthetic-only. `t64.model-result` v1 is separately a native probe with no guest verdict and must stay separate ([`result-protocol.md`](../../../docs/spec/result-protocol.md)). Keep v1 unchanged. For a real schema version, require actual build/profile identity, non-null state digest, fixture bytes digest, input schedule digest, captured log digest, guest tick/stop and the same six closed outcome names. A real-run `pass` must also match the fixture’s exact expected transcript; `PASS` plus `Done!` alone is insufficient. The result checker should accept old v1 and the new version as two explicit contracts, reject unknown fields in both, and continue refusing model results as guest evidence.

Preserve precedence: malformed arguments/setup, digest/capture/report errors and process failures are harness errors; a missing fixture is `missing-fixture`; invalid or unexpected non-empty guest output is a guest failure; **empty captured output is `boot-fail` even when guest time reached the bound**; only non-empty incomplete output at the guest-time bound can be timeout; pass requires the positive fixture-specific match. Current v1 already encodes empty-output before guest-bound and lists both `empty-halt` and `empty-bound` controls. Re-run those controls against actual guest execution where feasible, with a real zero-output looping fixture as the clean no-output/bound case. Synthetic cases remain supervisor/protocol regressions, not CPU evidence; do not demand that every synthetic runner misbehavior be reproduced as ROM behavior.

## Supervisor fixture binding — required before guest evidence

Current `check_fixture()` opens, hashes and closes the source path; later the child receives that same path and reopens it. The protocol itself names this Phase 1 limitation and requires the verified descriptor or a private copy before real-ROM results can attest executed bytes ([`runner/t64_supervisor.c`](../../../runner/t64_supervisor.c), [`result-protocol.md`](../../../docs/spec/result-protocol.md)).

**Recommend private copy, then descriptor only.** In the existing private per-run directory, create an exclusive temporary file, stream-copy the source while enforcing the size bound and hashing the copied bytes, compare that hash to the pinned digest, finish all writes, sync, make the copy read-only (mode `0400`), close the writer, reopen read-only, verify the copy digest/length, unlink its pathname, rewind and pass only that descriptor to the child. Do not pass the original fixture pathname. The guest runner must feed the bytes read from that inherited descriptor to core admission and bind the result digest to the admitted bytes; it must never reopen the caller path. Protect and hash the input schedule the same way (or parse it into a canonical owned schedule before guest start). Close descriptors and remove private files on every exit path. Missing source remains `missing-fixture`; symlink/special/unreadable/oversize, wrong hash, interrupted/short copy, temp-file or descriptor setup/read failures refuse to launch and yield the existing harness-error family. No guest state or pass result is produced on refusal.

The current hostile controls cover runner report/capture paths but not replacement of the input fixture after digesting it. Add a synchronized adversarial case: let the supervisor verify and start a runner that waits before reading, replace or rename the original source path, then release it. The runner must admit bytes from the inherited descriptor; result digest and a runner-reported digest of the admitted buffer must equal that original digest, and the replacement must not affect output. Also prove unreadable/replaced descriptor setup cannot launch or pass. This is the direct WR-06 acceptance test; hash equality without the runner’s descriptor-backed admission check is insufficient.

## CI proof and limits

Pin fixture build inputs and build the ROM identically in each matrix leg when distribution is restricted to build-only; if cleared for internal artifact distribution, build once and verify its digest on each leg. Run the same guest fixture, profile, input schedule and guest-time bound on Linux/GCC and macOS/Clang. Compare profile/content/input/fixture/log identity plus `state_digest` across legs; do not compare full result bytes if host compiler build identities differ. Assert exact expected log bytes in addition to the canonical result, and vary host advance slice sizes while requiring identical guest-time results/digest. Run the model probe and existing synthetic 19-case controls in their own evidence lanes; a model match or synthetic `pass` must never satisfy the guest fixture check.

These checks prove this authored fixture reached its expected path through this pinned boot profile and that the selected digest is deterministic across the matrix. They do not prove broad commercial-ROM compatibility, controller input consumption, every IPL3/CIC variant, full real-ISViewer hardware behavior, or “boot solved.”
