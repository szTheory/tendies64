# Phase 2 Decision Research A — Instance State, Identity, Ordering and Digest

**Scope.** Decision-focused proposal for machine memory ownership, profile/build identity, event ordering and stop bounds, and canonical state digest/trace separation. The current facade is provisional; none of these proposals freezes the public ABI before Phase 10.

**Evidence boundary.** Project policy is in `AGENTS.md`, ADR-0002 and ADR-0006, the Phase 1 context, `REQUIREMENTS.md`, and the Phase 2 roadmap entry. The current core facade is only a synthetic-runner seam. No hardware arbitration or DMA behavior is established by it. The only external technical fact used here is SHA-256's standard definition, specified by [NIST FIPS 180-4](https://csrc.nist.gov/pubs/fips/180-4/upd1/final); the existing helper is authored in-tree and already has FIPS vectors. Device priorities and hardware tick values remain primary-source questions, not assumptions in this proposal.

## 1. Mutable memory ownership

| Option | Pros | Cons | Failure modes | Recommendation |
|---|---|---|---|---|
| Host-supplied, per-instance opaque arena and memory spans; core owns their guest meaning | Fits ADR-0002's host-provided memory and no-heap rule; one instance owns scheduler/register/RAM state; direct byte spans are easy to hash; core controls address-map semantics | Host must provide correctly sized, aligned, stable, non-overlapping storage; profile growth changes required size | Shared or reused span leaks state between instances; bad size/alignment can corrupt memory; mutating borrowed ROM invalidates execution identity | **Rec for Phase 2.** Host provisions storage before initialization; core performs guest memory accesses directly and makes no host calls during `advance()` |
| Host read/write callbacks for every guest access | Flexible backing stores and sparse mappings; host can instrument accesses | Callback behavior becomes part of deterministic execution; digest and transactional ROM refusal need callback readback; reentrancy and interleaving become harder to constrain | Callback reads vary, mutate shared bytes, block, or invoke host services; callbacks make an otherwise identical run diverge | Rec only if a concrete host mapping need emerges and callback determinism, lifetime, aliasing, and digest semantics can be enforced |
| Core-owned fixed global memory or public concrete instance struct | Simple address arithmetic; no callback contract | Violates multi-instance isolation or freezes layout; fixed capacity blocks later profiles; public struct exposes ABI and padding | Two instances alias global RAM; later RDRAM/profile change breaks callers or digest portability | Do not use |

**Proposed contract.** The host supplies one aligned opaque state arena per instance, sized by a provisional profile sizing query (or by the runner's host allocation callback), plus stable mutable RAM spans and a read-only content span. The core stores all mutable machine metadata—guest tick/counters, event queue, device registers, DMA progress, pending interrupts, and per-instance references—in that arena. RDRAM and other writable guest memories are disjoint per-instance spans; immutable ROM bytes remain host-owned and unchanged until unload. The core never allocates, opens files, or asks the host for bytes while advancing. Creation validates all span lengths, alignment, non-aliasing and profile values before mutation; malformed or undersized arguments are refused without touching caller memory. Admission validates the entire input before committing its content identity or machine-visible state. A rejected admission leaves the prior state digest unchanged.

This interprets ADR-0002's “memory comes from host callbacks” as host-provisioned memory, not a callback on each guest load/store. If ADR-0002 intended per-access callbacks, resolve that wording in the Phase 2 decision record before implementation; do not silently add callback behavior to the scheduler.

**Reversal evidence.** Split spans further if measured host integration or expansion profiles show a contiguous arena is impractical. Reconsider per-access callbacks only with a concrete required backend and tests proving read/write determinism, non-reentrancy, transactional failure behavior, and identical digests across isolated/interleaved instances.

## 2. Profile identity and build identity

| Option | Pros | Cons | Failure modes | Recommendation |
|---|---|---|---|---|
| `profile_id` string alone (or hash only the name) | Small and readable | Does not encode settings; the same name can silently change semantics | A region, RAM size, timing tier, boot path, or sync-quantum change keeps the old identity | Do not use |
| Human-readable ID plus SHA-256 of a canonical profile descriptor; separate build ID | Captures behavior-affecting settings; existing result protocol already carries both profile fields and `build_id`; profile identity stays stable across compiler builds | Requires a versioned descriptor and strict canonical serialization; profile values need evidence | Hidden defaults or omitted scheduler/timing fields make different machines hash alike | **Rec.** Hash every behavior-affecting machine/profile parameter; report build identity separately |
| One combined hash of profile, source build, toolchain and runtime settings | Identifies one execution configuration | Conflates machine semantics with implementation and host configuration; cross-compiler results get different machine identities | A compiler change appears to be a profile change; result comparisons become harder to interpret | Rec only for an artifact/build manifest, not the profile hash |

**Proposed contract.** `profile_id` is a stable label (for example, a short lower-case N64/NTSC/cartridge/4-MB/open-IPL3/T1 name), while `profile_hash` is SHA-256 over the canonical UTF-8 `t64.profile` descriptor using the result protocol's sorted-key, no-extra-whitespace, one-LF form. Include schema/version and every setting that can change guest-visible behavior: exact console revision, TV standard and region, RDRAM size, boot route, expansion and peripheral set, CPU timing tier and cost-table version, guest-time base, CPU-to-RSP sync quantum, and scheduler-order version. Do not infer region or TV type from ROM country bytes. Do not publish a “known” value for an unverified hardware field: Phase 2 must cite a pinned primary document or explicitly label the field as an unresolved blocker to hardware claims. Profile limits/evidence remain documented separately, as required by PROF-04.

`build_id` remains separate and is emitted in every result. Set it from version, source revision, target/toolchain identity, and declared build configuration; omit timestamps and host paths. A dirty/local build needs a deterministic tree/config identity or a local-only label, never a wall-clock stamp. Build identity must not enter `profile_hash` or `state_digest`; otherwise the same machine state from the Linux/GCC and macOS/Apple Clang matrix cannot compare equal. Preserve the Phase 1 `synthetic-stub` / `+synthetic` stamp for synthetic evidence.

**Reversal evidence.** Add profile fields when a sourced setting demonstrably changes behavior and was omitted; bump the profile schema or identity version if canonical rules change. If result review shows that the chosen `build_id` cannot distinguish materially different tested artifacts, strengthen the build manifest identity without changing profile identity.

## 3. Total order and bounded advance

| Option | Pros | Cons | Failure modes | Recommendation |
|---|---|---|---|---|
| Per-instance FIFO sequence at each guest tick: `(tick, enqueue_sequence)` | Small deterministic total order; independent of host call/slice size; causal order is explicit; no unsupported hardware-priority claim | The order follows deterministic event producers; device priority is not implied | Nondeterministic producer order, sequence wrap, silent event drop, or host slice dependence | **Rec for the skeleton.** Make tie-breaking a named scheduler-order version in the profile |
| Fixed `(tick, phase, device-rank, local-sequence)` priority | Encodes explicit device arbitration and stable ordering | Requires sourced device priorities and careful same-tick rescheduling rules | Project invents hardware priority, or a newly queued event sorts “before” already processed work | Rec only after the relevant ordering rule is verified against primary sources |
| Host-driven slice/event polling or per-device independent clocks | Easy to call from a runner; can mimic coarse devices | Host cadence can affect order and final state; synchronization needs extra policy | Different slice sizes or interleavings yield different state | Do not use as canonical guest-time control |

**Proposed contract.** One single-threaded scheduler owns an integer guest tick and a bounded per-instance queue. Events are ordered by increasing tick, then by a monotonically increasing per-instance enqueue sequence assigned at insertion. Equal-tick order is a project-defined deterministic tie-break, not a statement about N64 bus arbitration. Device handlers may schedule only at the current or a later tick. Queue full or sequence exhaustion reports an explicit deterministic core error; never drop an event or wrap. No host clock drives the tick. Device-specific order and PI/SP DMA completion timing remain separate, source-backed contracts.

The runner requests absolute bounds. A guest-time bound is inclusive: process all queued events with `event.tick <= bound`, then report the bound at exactly that tick. A halt at the bound reports `guest-halt` (matching the current synthetic facade's behavior). Instruction and frame bounds are cumulative counters and stop immediately after the event that reaches the requested count; a Phase 2 synthetic test may inject named synthetic instruction/frame events to verify this mechanism, but they are not CPU instructions or VI frames. A bound below the current absolute counter is refused with no state change. If the queue empties before the bound, report a distinct quiescent/idle stop at the current tick; do not claim the bound was reached. Keep slice size out of the core contract; runner chunking may change, but the final state and stop reason for the same bound must not.

**Reversal evidence.** Replace FIFO tie-breaking with sourced phase/device priorities only when pinned primary evidence or hardware-derived measurements require it. Version that policy in the profile and show compatibility tests where equal-tick cross-device cases change. If slicing changes digests, the scheduler contract or implementation is wrong; that is a defect, not evidence to bless another order.

## 4. Canonical state digest and trace noninterference

| Option | Pros | Cons | Failure modes | Recommendation |
|---|---|---|---|---|
| Hash raw instance-struct bytes | Very little code | Includes padding, pointers, host layout and possibly trace buffers | Cross-compiler/OS mismatch; uninitialized padding creates unstable hashes | Reject; conflicts with ADR-0002 |
| Versioned canonical field serialization, then SHA-256 | Portable; explicit fields and byte order; streams without a large allocation; reuses the authored helper | Serializer must be updated with every state field; encoding needs golden vectors | Omitted pending event/device state gives false equality; wrong byte order changes digests | **Rec.** Reuse `t64_sha256` and add a core-visible, testable canonical writer |
| Canonical JSON of complete machine state | Human-inspectable and easy to compare | Large for 4-MB RDRAM; JSON writer/parser complexity in core; allocation-free streaming is awkward | Text formatting or omission errors; pulls host-side JSON machinery into the determinism boundary | Rec only as an external debug/export view, not the core digest format |

**Proposed contract.** Hash a domain tag and state-format version, then fixed-width big-endian profile hash, content digest, guest tick/counters, architecturally meaningful mutable state, RAM bytes in a specified address order, device registers, pending interrupt state, and queued events in logical `(tick, sequence)` order. Include every value that can change future guest-visible behavior. Exclude C padding, pointers/callbacks, host metadata, build ID, host timing, trace buffers/trace enablement, and drained log-capture buffers. The result protocol already records `fixture_digest` and `log_digest`; keep those as separate evidence. Treat the content digest as immutable machine input identity so a state reached with different content does not alias merely because current RAM bytes happen to match. Digest serialization reads the same per-instance memory that execution uses.

The trace path is an observer. Record bounded, guest-tick-stamped copies at device boundaries into a caller-provided trace buffer; drain after `advance()` and never call a host sink from inside an event handler. A full trace buffer drops trace records and reports an observer-side dropped count, but does not pause, reorder, or stop the machine. Trace configuration and bytes are outside the digest. The same input and bound must therefore produce the same state digest with tracing enabled or disabled. Trace completeness is asserted only when the test buffer was sufficient; overflow must be visible.

Reuse `tools/common/t64_sha256.c` / `.h`, whose fixed-width streaming API, explicit big-endian block encoding, no-global-state implementation, and NIST vector tests fit the need. To keep the core lint authoritative, make the single implementation part of the `core/` linted source set (or otherwise lint the exact object linked into core); do not link an opaque host-only helper around the core check. SHA-256 here is an identity digest, not a MAC or authenticity claim.

**Reversal evidence.** Change the encoding only with an explicit state-format version and cross-platform golden vectors. Add a field if mutating it changes future behavior and a paired-state test demonstrates the digest failed to notice. Trace may move to another buffer/callback boundary if profiling shows material overhead, provided the traced/untraced digest invariant and non-reentrancy remain proven.

## Failure modes and verification proposal

- **Isolation:** run two instances with separate storage in alternating slices, then compare each final digest and logs with its isolated run; run a negative control that intentionally aliases one mutable span and ensure the harness detects it.
- **Identity:** verify a canonical descriptor has a stable profile hash across supported toolchains; change each behavior-affecting field one at a time and require a changed hash; vary build ID only and require the profile hash/state digest to remain equal.
- **Scheduler/bounds:** equal-tick events follow enqueue order; inclusive tick bound stops exactly at the requested tick; halt-at-bound wins; lower bounds refuse unchanged; synthetic instruction/frame counters stop at exact counts; changed runner slice size produces the same result. Label synthetic events so no CPU/VI behavior is inferred.
- **Digest:** published SHA vectors plus golden state encodings; perturb each included field/RAM byte/pending queue event and require a digest change; perturb padding, pointer values, build ID and trace buffer and require no digest change; trace-on/off final digest equality, including visible overflow behavior.
- **Memory/refusal:** short/unaligned/overlapping spans and malformed/oversized/unknown-byte-order content are refused before commit; compare the digest and relevant caller bytes before/after refusal. Fuzz the production admission parser under ASan and UBSan through every header-dependent read, as Phase 2 requires.
- **Core boundary:** run the existing core lint on the exact linked core objects; no heap, I/O, clock, entropy, thread, mutable file-scope state, or out-of-instance machine state.

These are proposed acceptance checks, not run results. They intentionally establish determinism and honest skeleton boundaries, not CPU/VI behavior or hardware accuracy.
