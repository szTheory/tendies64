# Phase 2 decision research: ROM admission and parser safety

Status: recommendation for Phase 2 discussion; this is not final CONTEXT or a plan.

## Options

| Option | Pros | Cons | Complexity | Recommendation |
|--------|------|------|------------|----------------|
| Accept only canonical big-endian (`z64`) bytes; core owns a copy | Smallest parser and no normalization path, simple canonical digest | Rejects two established dump byte orders, puts format conversion on every caller | Core loader + size/header checks; Risk: avoidable caller failures | Rec if deliberately limiting the first content API to authored canonical images |
| Accept all three known byte orders and retain the caller's buffer | No full-image copy, lower transient memory | Requires a lifetime/immutability contract, permits caller mutation after admission, makes aliasing and multi-instance ownership harder | Parser + cross-boundary lifetime rules; Risk: stale or modified content | Rec only if a later host API explicitly guarantees immutable storage for the instance lifetime |
| Accept all three, normalize into a staged core-owned image, then swap on success | One canonical representation, host memory is borrowed only during the call, refusal can preserve the whole instance, digest independent of input order | One bounded allocation/copy, transient host-plus-core memory | Core loader, canonical buffer and digest; Risk: allocation failure, bounded by the cap | Rec if the instance owns admitted cartridge content, as the current opaque-instance direction implies |

**Rationale:** Use the third option for this phase: the core owns content after admission, and the host remains responsible for reading files. Keep the C17 choice from ADR-0002 unchanged; the Phase 1 parser only read four bytes and its fuzzing is explicitly not production safety evidence. Primary source: the [Nintendo 64 ROM Registration Instructions](https://ultra64.ca/files/documentation/online-manuals/man-v5-1/info/submission/ntsc/01-04.html) define the title, reserved area, four-byte game code and version offsets at `0x20–0x3F`; they do not specify dump-file endianness. Secondary format reference: treat `z64`/`v64`/`n64` byte patterns from the [N64 ROM format reference](https://n64dev.org/romformats.html) as file-format conventions, not machine or hardware behavior. Do not infer profile TV/region from the header: the Nintendo registration contract defines a game-code field, and interpreting one of its bytes as a country hint does not select a hardware profile. The [Nintendo 64 Programming Manual's ROM image packer section](https://ultra64.ca/files/documentation/online-manuals/man-v5-1/pro-man/pro05/05-06.htm) confirms that ROM images are the packed host artifact. The current runner already uses 64 MiB as a fixture safety cap; reusing that bound is a project policy, not a claim that hardware cannot address larger media. [LLVM's libFuzzer guide](https://llvm.org/docs/LibFuzzer.html) requires a Clang toolchain for its `-fsanitize=fuzzer` runtime; the normal CI matrix uses the default compiler on Ubuntu and Apple Clang on macOS, so keep the required bounded campaign in a standard C17 deterministic driver under the existing ASan preset rather than making CI depend on libFuzzer availability.

## Recommended admission contract

- Input is one raw byte span. The core opens no path, unpacks no archive, applies no patch, and ignores filename extensions. The caller must provide `len` readable bytes when `bytes` is non-null. `bytes == NULL` is refused before any read; all arithmetic and length checks happen before indexing or allocation.
- Accept only `0x1000 <= len <= 0x04000000` (64 MiB) and `len % 4 == 0`. The 4 KiB minimum and 64 MiB maximum are first-profile bounds; 64 MiB reuses the runner's existing cap and is not described as a hardware ceiling. Reject smaller/truncated, larger, non-word-sized, and unrecognized-order images. Make the maximum a named profile/admission constant so later evidence can change it without changing machine semantics.
- Detect bytes at offset `0`: `80 37 12 40` is canonical big-endian, `37 80 40 12` swaps each byte pair, and `40 12 37 80` reverses each 4-byte word. Ignore the extension. Convert accepted input to canonical big-endian bytes before storage and hashing.
- Parse the fixed 64-byte header through explicit offsets and bounded byte reads, not a cast to a packed/native struct. Copy the normalized `0x00–0x3F` prefix as fixed bytes, then expose only fields needed by this phase: title `0x20–0x33`, Game Code `0x3B–0x3E`, and version `0x3F`. Retain text fields as fixed byte arrays, not NUL-terminated strings. Require only the image-size and recognized-order constraints above; do not reject unknown title, reserved, game-code or version values. The 64-byte file header is available for every admitted span, so field reads must not use header-provided offsets or lengths.
- Use the header's `0x3B–0x3E` bytes as registration metadata only. In particular, changing byte `0x3E` must not change the selected profile's TV type or region.
- Build a temporary candidate containing the canonical owned image, parsed header, length and canonical SHA-256. Only after parsing, normalization and digest completion succeed, swap the candidate into that instance and reset its machine state to the profile's initial state. Then release the old image. For every refusal (null, short, over cap, non-multiple-of-four, unknown order, and allocation failure), do not change ROM ownership, header, scheduler, device state, profile identity or digest. No shared/global staging buffer.
- Keep the state/content digest serialization explicit and padding-free. `tools/common/t64_sha256.*` is currently built as host tooling; compile the same small, pure implementation into a core-safe target or relocate it to a dependency-neutral location. Do not make `t64_core` depend on the entire host `t64_common` library.

## Required evidence and bounded fuzzing

- Generate only project-authored byte arrays at test runtime: a 64-byte synthetic header with distinct values in every field, copied into a 4 KiB buffer for each accepted byte order. Never use a commercial image, IPL/PIF data, copied image fragment, or an external ROM fixture. The rights policy keeps binaries and protected images out of the repository and CI; byte arrays are locally authored test inputs, not image fixtures.
- Add table-driven cases for all three order signatures and their normalized first 64 bytes; `len` values `0`, `1`, `0x3F`, `0x40`, `0xFFF`, `0x1000`, `0x1001`, cap-minus-one, cap, cap-plus-one; malformed signatures; and `NULL`. Use the size check directly for cap-minus-one and cap boundaries; allocate one `cap+1` synthetic span to exercise the over-cap admission refusal without reading it. For every refusal, first load a valid synthetic image, set non-default guest state, compute the canonical state digest, attempt the refusal, and assert digest and all observable instance outputs are unchanged.
- Fuzz the production fixed-header parser (the same core function used by admission), not a copy or stub. Include short prefixes `0..63`, plus generated canonical valid headers for all three formats. A deterministic mutation driver should mutate each header offset and boundary independently, then run 250,000 mutations over the 64-byte header from pinned seed `0x7a64c0de`; assert parse invariants and verify each exposed field against its source bytes. ASan/UBSan must execute the valid-header path for all formats and reach every field read. Log only seed, case count and sanitizer result.
- Keep the standard fast `./scripts/gate.sh` unchanged in CI and add no separate CI job. The existing CMake `asan` preset already builds the project with ASan and UBSan and is deliberately outside the gate. Wire the deterministic campaign as a named CTest test (for example `fuzz.rom-admission`) and reproduce it with:

  ```sh
  cmake --preset asan
  cmake --build --preset asan
  ASAN_OPTIONS=detect_leaks=1 UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1 \
    ctest --preset asan --tests-regex '^fuzz\.rom-admission$' --output-on-failure
  ```

- If a longer coverage-guided run is useful locally, make it optional and Clang-only: LLVM documents `-fsanitize=fuzzer,address,undefined` for recent Clang builds, while GCC does not provide libFuzzer. Preflight the local compiler with `clang -fsanitize=fuzzer -x c - -o /tmp/t64-fuzzer-check` using a minimal `LLVMFuzzerTestOneInput` source, and use the deterministic CTest campaign as the portable required evidence. Keep any libFuzzer corpus in a temporary/build directory and pin the seed/run bound in the command; do not commit crash inputs until they are reviewed as authored text.

The existing SHA-256 helper is suitable for bounded, non-empty spans; this review found no relevant memory-safety defect in it. The Phase 1 spike's four-byte parser remains useful only as a basic signature precedent, not as evidence for this contract. `.planning/state.json` is generated, currently untracked, timestamped resolver state that duplicates the tracked human-readable `.planning/STATE.md`; recommend adding that exact path to `.gitignore` so generated bookkeeping does not keep appearing in the worktree.
