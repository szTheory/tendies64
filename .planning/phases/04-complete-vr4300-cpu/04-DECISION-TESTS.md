# Phase 4 test-ROM integration and evidence decision

**Status:** Recommended implementation boundary; no build, install, ROM run, or test result was produced by this research.  
**Scope:** Local `nemu64-test` diagnostic input for Phase 4 CPU groups, its provenance and output boundary.  
**Owner policy:** D2 already permits local builds and runs while rights are pending. That permission does not extend to committing or publishing the ROM, derived output, or results.

## Comparison

| Option | Pros | Cons | Complexity | Recommendation |
|---|---|---|---|---|
| Run the unmodified upstream `base` ROM locally | Uses the exact upstream source revision and complete default set; retains the upstream self-checks and final feature-level summary | The default set mixes CPU with RSP, RDP, PIF, RDRAM, MI, cartridge and SP-memory tests; current output does not report CPU-domain pass totals; default ROM build embeds an unqualified libdragon IPL3 and Geneva 9 font; current Tendies64 real runner refuses this fixture | Separate build/run adapter and private outputs; boot, graphics and device assumptions span beyond the Phase 4 profile -- Risk: accidental RSP/device scope expansion, unclear embedded assets, aggregate output mistaken for CPU status | Rec if exact unmodified-base behavior becomes necessary after component and asset qualification; do not treat its aggregate result as SC4 CPU-group evidence |
| Build a pinned, local-only CPU source variant with a project-owned inventory/report overlay | Keeps the test code tied to a fixed upstream commit; selects and counts CPU groups explicitly; emits per-test outcomes while preserving upstream test identities; allows non-CPU and later timing groups to be listed as skipped/deferred; can remove framebuffer/font assets and select a separately cleared IPL3 | It is a documented derivative of upstream `base`, not an unmodified upstream ROM; CPU groups and status protocol must be project-defined; the generated binary remains local-only while any compiled asset/dependency rights are pending | Local source overlay, exact test inventory, output adapter and separate private execution path; no new CI lane -- Risk: omitted tests, package/toolchain trust, incomplete boot equivalence | **Rec if preserving SC4 with bounded CPU scope**; retain every CPU group's pass/fail/incomplete status, and record skipped non-CPU groups explicitly |
| Use only project-authored CPU vectors and permitted fixtures | Independent expected values can be checked from pinned primary CPU documents or derivations; results can remain in the existing public/native gate; no external ROM or package-install pipeline | Does not provide `nemu64-test` per-group diagnostic status and cannot silently replace SC4; narrower external cross-check coverage | Native CPU component tests and, where useful, separately authored permitted guest fixtures -- Risk: local blind spots if treated as a substitute for the pinned diagnostic | Rec as the public completion evidence and independent oracle; pair with the local-only variant to satisfy the diagnostic purpose of SC4 |

**Rationale:** Keep the existing SC4 requirement and D2 boundary. The CPU-only overlay is the smallest approach that can report a complete, pinned status for each CPU group without making Phase 4 depend on RSP/RDP/PIF behavior. Project-authored vectors remain the acceptance evidence whose results may be checked in or reported publicly; the external ROM and every result derived from it stay private while rights are pending. The overlay shares Tendies64's canonical machine through a separate local adapter and does not expand the public hello runner or collector.

## Pinned upstream observations

As of 2026-11-11, read-only Git metadata identifies [`thelemmy/nemu64-test`](https://github.com/thelemmy/nemu64-test) as a public repository with default branch `main` at `9a8b9f7d94ee2f6f57d7feed70c98c22cdc30e6c`, pushed 2026-09-08. The repository reports 4 stars and 2 forks. Tendies64's `fixtures/manifest.json` already pins this exact revision. The upstream root license is MIT; this permits the upstream source to be locally built and modified with its notice retained, but it does not clear the generated ROM or the contents bundled into it. See the [pinned README](https://github.com/thelemmy/nemu64-test/blob/9a8b9f7d94ee2f6f57d7feed70c98c22cdc30e6c/README.md), [pinned license](https://github.com/thelemmy/nemu64-test/blob/9a8b9f7d94ee2f6f57d7feed70c98c22cdc30e6c/LICENSE), and [pinned Cargo manifest](https://github.com/thelemmy/nemu64-test/blob/9a8b9f7d94ee2f6f57d7feed70c98c22cdc30e6c/Cargo.toml).

The upstream README's `262` example is illustrative, not the inventory for this pinned revision. The source has a flat `default_tests()` list and its `Test` interface can run zero or many values for one registered test. Its `Level` categories are BasicFunctionality, RarelyUsed, Weird, RDPBasic, RDPPrecise, Timing, COP0Hazard, Cycle, PoorlyUnderstoodQuirk, and StressTest; the final summary reports feature-level aggregates (Base, Timing, Cycle, CP0-hazards and poorly understood quirks), not CPU-domain totals. There is no upstream CPU-only feature. See pinned [`src/tests/testlist.rs`](https://github.com/thelemmy/nemu64-test/blob/9a8b9f7d94ee2f6f57d7feed70c98c22cdc30e6c/src/tests/testlist.rs) and [`src/tests/mod.rs`](https://github.com/thelemmy/nemu64-test/blob/9a8b9f7d94ee2f6f57d7feed70c98c22cdc30e6c/src/tests/mod.rs).

A static count of `Box::new(Test)` registrations in `default_tests()` gives these *candidate CPU module groups* and registration counts: `address_error_exception` 11; `arithmetic` 396; `cache` 53; `cop0` 44; `cop1` 76; `cop_unusable` 27; `endian_re` 9; `exception_instructions` 27; `jumps` 23; `overflow_exception` 15; `privilege` 6; `tlb` 46; `tlb64` 11; `traps` 14. These sum to 758 registered test objects. They are source observations only: they are not upstream CPU-group definitions, are not counts of `Test::values()` cases, and are not pass/fail denominators. The same list has 18 registrations from `timing`; individual test levels can also place registrations in separate feature lanes. Final Phase 4 counts must be generated by the project-owned allowlist and adapter from the pinned source, with exact test names and value counts. Do not use these constructor counts or the README example as the reported runtime inventory.

The observable guest channel is line-oriented text over ISViewer, not a canonical JSON test protocol. The README documents a writable buffer at `0xB3FF0020..0xB3FF0220` and a 32-bit length write at `0xB3FF0014`; source logs a test start and failure details, then totals by feature level. The output does not give an explicit per-test pass record. The overlay therefore needs a small project-authored record for each executed value/test and a completion marker, bound to the exact source revision, patch hash, group inventory hash, profile and ROM digest. Its consumer must distinguish `pass`, `fail`, `incomplete`, `not-run`, guest stop, and harness error. A group passes only when its exact expected inventory ran to completion and no member failed.

Cargo's official [`cargo install` documentation](https://doc.rust-lang.org/cargo/commands/cargo-install.html) says a published binary crate's included `Cargo.lock` is used by default; `--locked` does not change resolution if no lockfile is present and warns in that case. Therefore the README's `--locked` flag alone does not establish which dependencies are pinned. `nust64` has a separate dependency graph from the test ROM's own `Cargo.lock` and must be audited separately.

## Integration and evidence boundary

- The current `t64_real_fixture` allowlist admits exactly seven rights-cleared project-authored `hello-*` ROM identities. The pending `nemu64-test-base` manifest entry is not admitted by that list.
- `t64-supervisor --real` and `t64-runner-real` hardcode `hello-openipl3`, its warm profile, fixed input/bound, authored transcript and completion PC. `scripts/collect-boot-evidence.sh` requires those same hello identities and emits the public `t64.boot-evidence` record. Do not add the external ROM to this allowlist or collector.
- Use a separate *local diagnostic adapter* over the same Tendies64 canonical machine implementation. It may share the verified-input, bounded execution and result-checking seams, but must not fork machine behavior. Keep the external fixture and all derived records under an ignored private local path; do not write to `build/evidence`, set up an Actions artifact, add a CI job, or run this fixture in public CI.
- Build the overlay from the pinned upstream commit in an isolated local checkout. Filter the registration list by a project-owned exact test-name allowlist. Record every omitted upstream group and its source count as `skipped-non-cpu` or `deferred-phase`; preserve separate `Timing`, `Cycle`, `COP0Hazard`, and poorly-understood lanes rather than folding their status into Base. Give CPU tests that cannot be reached because of a boot/core dependency a `blocked` or `incomplete` status, never `pass`.
- The boot path documented by upstream uses RSP DMA before the test list, including an out-of-range RDRAM source and a transfer longer than IMEM that wraps in IMEM. The suite also registers RSP/vector, SP-memory, RDP, PIF, cartridge, MI and RDRAM tests. Tendies64's current warm profile has no RSP instruction engine, no VI/RDP implementation and only a narrow 4 MiB/no-expansion prepared state; its exact zero-source DMA exception is limited to a pinned tuple. A broad suite pass would therefore cross Phase 4 into Phase 5/6 and video/PIF work unless tests are explicitly filtered. Do not silently expand those machine capabilities or call their skipped rows CPU evidence.
- Keep project-authored CPU vectors with independently sourced expected values as the Phase 4 acceptance gate. Do not use another emulator, an external ROM's expected values, or its observed output as the independent expected-value source. D2-derived local status is useful diagnostic evidence, but remains private and must not support public claims while D2 is unresolved.

## Vertical-slice sequence

1. **Freeze the diagnostic contract in the Phase 4 plan.** Define the project-owned CPU module/group map, exact source test-name inventory, value-count semantics, `Timing`/`Cycle`/`COP0Hazard` treatment, non-CPU skip inventory, result statuses and completion rule. Preserve SC4's per-group status requirement; a failure in a group is a reported diagnostic, not a reason to demand every group pass before the CPU work is reviewable.
2. **Complete pre-use qualification.** Audit the exact `nust64` crate and its separate lock/dependencies, Rust nightly and component provenance, upstream source/build inputs, font/framebuffer assets, selected IPL3, and ROM composition. Keep local-only rights statuses pending when evidence is absent. Do not install any tool until this record is complete.
3. **Create the source overlay and private inventory.** Use the pinned upstream source plus a project-owned deterministic patch. Remove the unclear font/video path; use an explicitly identified cleared IPL3 only after confirming input format and startup compatibility; instrument per-test/value outcomes and final completion. Hash the patch, inventory, toolchain, fixture and canonical output protocol in private metadata.
4. **Run through a separate local adapter sharing the canonical core.** Verify input bytes by descriptor/digest, apply the new CPU-enabled profile with its qualified executable seed and explicit guest/wall bounds, capture bounded ISViewer bytes, validate the result and classify each required CPU group. Keep raw captures/results private and check statuses against the exact inventory.
5. **Keep public completion evidence independent.** Exercise CPU edge, negative and refusal cases through project-authored native vectors with independent expectations in the existing gate. No new CI lane, cache, timeout policy or public external-ROM artifact is needed.

## Reversal evidence and unresolved blockers

- A documented per-file asset and generated-binary rights chain plus an owner resolution of D2 could permit a later public artifact/CI design; the repository MIT license or a matching digest alone is not that evidence.
- If the exact pinned `nust64` package cannot be correlated to reviewed source, its separate lockfile is absent/changed, its dependencies or build behavior are unacceptable, or the rustup toolchain cannot be sourced and pinned legitimately, do not install it. A project-authored packer using an already qualified target toolchain is a candidate alternative, but it must be costed and planned before use.
- If the overlay cannot remove the font/video dependency, cannot select a qualified IPL3, or cannot produce complete per-test records without changing tested CPU semantics, report that group as blocked and retain the unmet part of SC4. Do not substitute a monolithic aggregate summary or a synthetic model result.
- Exact runtime test/value counts, final patched-ROM SHA-256/size, boot compatibility with a cleared IPL3, complete bundled-asset inventory, and the `nust64` crate-to-source equivalence remain unresolved until the pre-use audit and authorized local qualification steps are performed. This research performed no install, build, ROM download or guest run.
