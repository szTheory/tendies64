## RSP profile integration

| Option | Pros | Cons | Complexity | Recommendation |
|--------|------|------|------------|----------------|
| Add RSP behavior to an existing CPU profile | Reuses its boot path, CPU behavior, and runner selection | Either changes behavior under an old identity or widens its old refusals; makes CPU-only evidence ambiguous | Profile predicates, SP routing, scheduler, digest, runner -- Risk: strict-profile leakage and stale result binding | Rec only if old profile IDs, hashes, and refusals may change |
| Add a distinct immutable RSP profile that shares CPU primitives and versions RSP state/events | Preserves every existing profile contract; keeps CPU code shared; binds SP/RSP policy and synchronization to a new profile hash | Requires exact profile gating across CPU helpers, SP registers, scheduling, and digest; more old-profile regression controls | Core profile, bus/SP, scheduler, state digest, runner -- Risk: missed future state or accidental old-profile routing | Rec if old identities/refusals remain fixed and RSP is a new capability |
| Version one generic diagnostic inventory/batch contract with component identity | Reuses the canonical parser, batch lifecycle, and aggregation; avoids a second protocol implementation | Current membership rules and completeness checks are CPU-specific; a broad schema change can admit cross-component members or weaken the sealed CPU set | Protocol, adapter, qualification, authored controls -- Risk: component confusion and denominator drift | Rec if component-scoped membership and the frozen CPU contract remain independently enforced |
| Add a bounded RSP diagnostic contract on shared protocol primitives | Keeps RSP membership, outcomes, and rights scope separate from the CPU inventory; can reuse canonical encoding and validation helpers | Adds schema and routing controls that can drift if they duplicate parser or aggregation logic | RSP protocol, adapter, qualification scripts -- Risk: parallel-parser divergence | Rec if RSP lifecycle or membership differs from CPU; share low-level protocol code, not the CPU-specific set |

**Rationale:** Static inspection of the sealed source projection and overlay shows RSP registrations are classified outside the required CPU lane; the current startup selector chooses a required CPU member, so that path does not reach RSP tests. The existing SP model holds HALT and has no RSP execution path; this is a source-route finding, not a guest run. Keep all current profile IDs, descriptor hashes, state digests, and refusal behavior immutable, add a separately gated RSP-capable profile that reuses CPU primitives, and serialize every new RSP future-state field under a new state domain while preserving existing digest bytes. Extend pre-use qualification with a fresh component-scoped source/value projection, complete overlay and dependency/tool audit, and reviewed RSP startup/data asset closure and rights; the current CPU qualification explicitly omits non-CPU RSP startup inputs. After those checks, build the selected diagnostic privately, inspect the exact executable/ROM composition, then run one selector-bound RSP member on a fresh machine with guest, wall, and capture bounds; authenticate the start/outcome/completion record and distinguish guest refusal, incomplete run, and harness failure. QA should first pin old profile/hash/refusal vectors, reject forged profile descriptors, prove unsupported RSP operations have no partial effects, and show each new state/event field changes the new digest; public CI, artifacts, and results remain stopped under the existing local-only rights boundary.
