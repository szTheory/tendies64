# Phase 5 Instruction Decisions

**Scope:** RSP scalar/vector execution and the permanent portable VU reference. These are project choices and evidence notes for planning; they do not claim a physical-console result. No HLE microcode path is authorized.

## Comparison and recommendation

| Option | Pros | Cons | Complexity | Recommendation |
|---|---|---|---|---|
| Portable C17 scalar SU plus lane-by-lane VU reference; keep it as the canonical path | One readable semantic implementation, explicit integer widths and byte order, portable across the current compiler/OS gate, suitable as the permanent comparison target | Careful helpers are needed for 48-bit arithmetic, saturation, flags, reciprocal state, and the different vector transfer forms; speed is unmeasured | Existing core and native tests; broad instruction surface, no new dependency. Risk: accidental host-endian or signed-overflow behavior | **Recommended for Phase 5.** Keep scalar as the only path until a repeatable benchmark shows it is a real bottleneck. |
| Add host-vector/ISA execution alongside the reference immediately | Could raise throughput for lane-parallel operations on a selected host | Adds duplicated semantics before a performance case exists; host lane order, saturation, flags, aliasing and accumulator behavior can diverge; every opcode then needs differential coverage | New host-specific paths and dispatch/tests. Risk: portability and reference drift | Rec if a named workload later measures the scalar VU as a material bottleneck and the target hosts are explicit; require lockstep comparison against the permanent reference. |

**Recommendation:** Make the scalar C implementation both the first implementation and the enduring oracle. “Scalar” describes how the VU math is expressed in C; the RSP instruction model still needs documented SU/VU pairing, ordering, and stalls. This keeps the deterministic reference simple while leaving a reversible optimization seam. Phase 5 should not add an optimized path without a measured need.

## Behavioral model

- Store each VU register as 16 explicit bytes. Define accessors for byte elements and eight 16-bit elements; lane 0 maps to the first big-endian register bytes as shown in the guide. Do not cast host byte arrays to `uint16_t *` or rely on host endianness. Keep vector loads/stores as opcode-specific transforms: normal, packed, long/quad/rest, and transpose forms are not interchangeable `memcpy`s, and partial load/store behavior differs.
- Keep eight independent 48-bit accumulator bit patterns. Use fixed-width unsigned arithmetic plus a 48-bit mask and explicit sign/field extraction. Avoid signed overflow, shifts of negative C values, and host-dependent narrowing. Test low/middle/high accumulator slices independently through VSAR.
- Model VCO, VCC, VCE, reciprocal input/result latches, and the SP control/status state explicitly. Instructions that consume or clear flags must have vectors for both flag-set and flag-clear inputs. Multiply tests must cover signed/unsigned product forms, accumulation, rounding, and signed/unsigned clamps at both sides of each boundary. Compare/select and clip tests must check both the selected destination lanes and all written/cleared flag bits.
- Implement VMOV as the VU scalar-element operation: copy `vt[element]` to the one destination lane selected by the instruction's `vs` field, preserving other destination lanes. Do not conflate it with MFC2/MTC2 or a whole-register move. Include same-register and untouched-lane cases.
- Treat reciprocal and reciprocal-square-root as deterministic table-driven operations with their two-instruction high/low input and result sequencing. The guide describes normalization, lookup precision, result assembly, and VMOV sequencing, but does not publish the lookup table contents. Do not substitute host floating-point `1/x` or `1/sqrt(x)` and call it hardware behavior. Keep edge/special-input expectations open until a public, rights-cleared source provides table values or an authorized hardware-derived vector set is found.
- The permanent reference and expected tests have separate roles. Expected outputs are authored constants with a short derivation from a cited primary rule or an identified hardware-derived vector record; never generate the only expected value by running the reference itself. Exercise all opcodes with edge and seeded input vectors. If an optimized path is added later, compare its complete architectural outputs against both the reference and independent expected cases.

## Exact first behavioral slice

Begin with one authored IMEM microprogram and seeded DMEM, executed through the real scalar/vector dispatcher: scalar arithmetic and a taken branch with its delay slot; one DMEM LQV/SQV pair using a nonzero byte position and checking untouched bytes; a VADD saturation case and a VMOV single-lane case; a scalar/VU pair with no hazard plus one load-use hazard that takes the documented stall; then BREAK. Assert the output bytes, all destination lanes, unchanged lanes, the relevant flags, retired PC, HALT/BROKE and interrupt-enable effect. Expected values must be written independently from the C reference and derived from the pinned guide. This small slice proves that instructions fetched from IMEM affect DMEM through the VU; it is not a microcode compatibility claim.

After that slice, extend instruction coverage in named groups: scalar/control and CP0; vector moves/transfers; add/sub/logic and flags; multiply/accumulate and VSAR; compare/clip/merge; reciprocal sequencing and table cases; then complete instruction, DMA, status and ROM-level coverage. Unsupported instructions must stop explicitly. No pass-through, no silent no-op, and no HLE substitution.

**Unknowns:** reciprocal/rsqrt table contents and exact special-input outcomes; precise cycle arbitration when DMA and SU/VU access single-ported DMEM/IMEM concurrently; and the specific behavior meant by the roadmap’s “halt corruption” item. Preserve these as unknowns rather than filling them with emulator behavior or assumed measurements.

## Entry-gate status and reversal evidence

The guide closes much of the entry gate: it documents ordered scalar/vector dual issue and register hazards; 8-byte DMA alignment and length rules, a one-active/one-pending request model, nominal peak throughput and setup overhead; single-ported IMEM/DMEM contention; status/BREAK/HALT fields; and VMOV plus multiply/clamp semantics. It does **not** specify a full cycle-by-cycle DMEM/IMEM arbitration result or the named halt-corruption behavior. Phase planning can proceed with the documented baseline only if those are explicitly bounded as unknown software-policy areas; if the success claim depends on matching either behavior, obtain a primary citation or an independently rights-cleared hardware-derived vector before freezing that claim. The reciprocal table is a separate implementation evidence gap even though it is not named in the entry gate.

Reverse the scalar-only choice only when a repeatable named workload shows the reference is the bottleneck, an optimized path has a bounded host target, and per-opcode differential tests cover full vector registers, accumulator slices, flags, DMEM output and reciprocal latch state with no differences. Promote any undocumented hardware claim only with a public primary source or an independently documented, rights-cleared hardware-derived vector; another emulator’s output or a suite pass alone is insufficient.
