# Phase 5: SP DMA and RSP timing decisions

## Evidence boundary

The [Nintendo Ultra64 RSP Programmer’s Guide](https://ultra64.ca/files/documentation/silicon-graphics/SGI_Nintendo_64_RSP_Programmers_Guide.pdf) (PDF cover v1.1; relevant sections marked Revision 1.0) is the primary reference reviewed here. It specifies in-order issue of at most one scalar-unit and one vector-unit instruction per cycle, no issue during register-conflict stalls, and programmer-visible hazard/bubble rules (pp. 39, 43–44). It specifies 8-byte DMA alignment, `(length - 1)` encoding, line/count/stride transfers, a two-request queue, peak 8 bytes per cycle with 6–12 clocks setup, and that IMEM/DMEM are single-ported and DMA accesses affect performance (pp. 96–97). It also documents the SP status command bits, read-to-set semaphore, 12-bit SP PC, BREAK halt/BROKE behavior, and optional SP interrupt on BREAK (pp. 85–88, 95, 170).

Those statements support architectural behavior and published performance constraints. They do **not** settle exact DMA completion/visibility edges, which bank access wins on a same-cycle conflict, CPU/RSP/DMA arbitration, or a deterministic “halt corruption” result. The guide says overwriting instructions at the active PC has undefined behavior (p. 96); no specific corruption outcome should be promised. The public [n64-systemtest README](https://github.com/lemmy-64/n64-systemtest) reports an over-4-KiB IMEM DMA wrapping within IMEM, which is useful vector evidence for bank wrap, but was not run or independently reproduced for this decision. A first-hand [DMA rate measurement](https://hcs64.com/dma.html) reports about 0.27 cycles per byte, but its polling overhead is estimated and measurement code is unavailable; it is not enough to choose an exact profile timing formula.

Local implementation observations: `t64_sp.c` validates each DRAM row against the selected 4 MiB profile, ignores low address bits, wraps payload through the selected 4 KiB bank, accepts active plus pending descriptors, and copies the full payload atomically from current source bytes at completion using `12 + payload_bytes/8` model cycles. `test_sp_dma.c` covers these choices, queue/refusal behavior, and scheduler FIFO ordering as native model tests; it does not establish hardware behavior. `machine-contract.md` explicitly labels the timing/visibility policy as model-only. The general skeleton has no RSP execution engine. The warm profile’s forced HALT, inert semaphore and zero PC are compatibility stubs for a profile with no RSP engine; do not carry them forward as hardware semantics. The scheduler orders events by `(guest_tick, sequence)` and currently advances the CPU by scheduled instruction events, but has no RSP cycle or shared-memory arbitration model.

## Alternatives

| Option | Pros | Cons | Complexity | Recommendation |
|---|---|---|---|---|
| New functional instruction-tier profile (`rsp-functional-v1`) | Small first RSP slice; makes scalar/vector instruction results and real microcode observable; can reuse deterministic event scheduling | Fixed instruction steps cannot express documented dual issue, stalls, or DMA contention; any DMA duration/visibility remains a declared approximation; likely migration if timing-sensitive microcode is a goal | RSP state/stepper, scheduler, SP register hooks, digest/profile and tests; risk: a useful functional core is mistaken for timing accuracy | Rec if Phase 5 is explicitly limited to functional output and timing-sensitive claims are deferred |
| New cycle-pipeline profile (`rsp-cycle-v1`) | Models the manual’s in-order SU/VU issue and published hazard/bubble rules; gives DMA and CPU/RSP interaction a meaningful guest-cycle domain; best fit for timing-aware microcode | More state and ordering edges; manual does not fully specify port arbitration, exact DMA edges/visibility, or halt corruption; deterministic model policy could be mistaken for hardware fact | RSP pipeline/scoreboard, scheduler, SP/DMA/MI hooks, profile/digest and tests; risk: false precision at undocumented conflicts | Rec if Phase 5 is expected to support timing-sensitive real microcode; keep unresolved DMA/port outcomes named profile policies until vectors establish them |

## Recommendation

Use a separate, versioned cycle-pipeline profile for the Phase 5 low-level RSP path, while leaving existing skeleton and warm profiles unchanged. Implement only the guide-backed issue, hazard, status, semaphore, PC, alignment, length, stride, and queue rules as hardware-supported behavior. Treat `12 + payload/8`, atomic-at-completion visibility, and the scheduler’s same-tick FIFO as current model choices, not inherited hardware facts. For DMA timing, expose setup and beat/visibility choices in the profile; the guide’s 6–12-clock setup range supports a bounded model choice, not one proven exact value. Defer claims about single-port priority, exact same-cycle CPU/RSP/DMA order, and halt corruption until a discriminating vector or primary source resolves them.

**Adversarial counterargument:** a cycle-pipeline implementation may cost more while appearing more accurate than the available evidence warrants. The manual is a programmer’s guide, not a complete arbitration specification; merely reproducing its hazard rules does not prove silicon timing. A functional profile is the safer delivery choice if the phase’s required outputs do not depend on timing. Keep the cycle profile’s unresolved ordering visible in its versioned policy, and do not describe it as cycle-accurate in those areas.

**Reversal evidence:** prefer the functional profile if authored integration vectors show the required Phase 5 microcode results are independent of timing and cycle work would block useful subsystem coverage. Tighten or change the cycle profile only when a reproducible vector or primary reference pins DMA setup/visibility, per-bank conflict order, CPU/RSP/DMA same-cycle order, or a specific halt-corruption effect.

## First minimal runtime tracer

Before tuning timing, add a deterministic observer record keyed only by guest RSP cycle: cycle/tick, CPU retirement PC when present, RSP PC and fetched SU/VU words, issued pair, stall reason/ready cycle, SP status and semaphore transitions, active/pending DMA token plus each 8-byte beat’s direction/bank/address, DMEM/IMEM access owner, and MI pending changes. Start with one authored, rights-clean microprogram that combines an independent SU/VU pair, a vector result dependency, one DMA beat to the same bank, and BREAK followed by CPU clear-HALT/restart; keep the trace and expected architectural state separate from host timestamps. This is a proposed instrument/vector only, not evidence from a run. It should expose whether additional focused vectors are needed for conflicting bank accesses, queued-DMA promotion, or halt/IMEM interaction.

## Entry-gate disposition

Partial evidence only. Primary documentation supports the core DMA shape and RSP pipeline rules, and the local tests cover the existing deterministic model. The gate still lacks a reproducible vector for exact DMA completion and progressive visibility, precise DMEM/IMEM contention order, CPU/RSP/DMA same-cycle scheduling, and any defined halt-corruption outcome. The last item may be undefined by design for an active-PC IMEM overwrite. Do not close those gaps by relabeling current skeleton behavior as silicon fact.
