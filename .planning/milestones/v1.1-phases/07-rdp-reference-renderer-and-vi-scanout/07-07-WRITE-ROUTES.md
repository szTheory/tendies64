# Plan 07-07 RDRAM Write Route Inventory

**Analysis Date:** 2026-11-17

Scope: production `core/` code paths that can mutate canonical byte RDRAM, the current sidecar lifecycle, and candidate hidden-coverage hook points. This is a code inventory; no tests or builds were run.

## Boot, Admission, and Other Direct Copies

- ROM normalization copies input into candidate image storage in `core/t64_rom.c:81`; admission transfers that owned image and metadata in `core/t64_machine.c:1850-1871`. This does not copy ROM bytes into RDRAM.
- OpenIPL3 prepared-entry functions copy the selected 0xfc0-byte payload from image storage to SP DMEM (`core/t64_machine.c:1360-1381,1401-1430`). No boot payload write to RDRAM is present.
- `core/t64_rdp_tmem.c:118-133` and `core/t64_vi.c:204-205` read RDRAM only. `core/t64_digest.c:282-283` hashes guest RDRAM; `core/t64_observe.c:12` exposes its bounded range. RDRAM protocol register writes in `core/t64_rdram.c` mutate device state, not byte RDRAM.
- Production direct mutation search found writes only in `core/t64_bus.c`, `core/t64_pi.c`, `core/t64_sp.c`, `core/t64_rdp.c`, `core/t64_rdp_raster.c`, and initialization/reset in `core/t64_machine.c`. Cache stores are staged in `core/t64_cache.c` and reach RDRAM through the bus writeback helper.

## Current Sidecar Ownership and Mapping Gap

- The existing `rdp_triangle_coverage` is a per-instance 1024×1024 `uint16_t` sample-mask plane (2 MiB), indexed by `y * T64_RDP_TRIANGLE_COVERAGE_WIDTH + x` (`core/t64_internal.h:108-113,788`; `core/t64_rdp_raster.c:561-563`). Raster ORs masks into it; it is not indexed by RDRAM byte address and has no CPU/PI/SP invalidation path.
- For machine/state version pairs 12/17, 13/18, and 14/19, creation appends aligned sidecar storage after `profile.rdram_bytes` in the single machine allocation (`core/t64_machine.c:1710-1729,1784-1795`). The `machine->ram` bus limit remains `profile.rdram_bytes`; the appended bytes are not guest RDRAM. `t64_machine_destroy()` releases that containing storage (`core/t64_machine.c:1801-1818`).
- The triangle sidecar is cleared on initial allocation and successful guest reset (`core/t64_machine.c:1792-1795,1486-1489`) and is serialized into the canonical digest for triangle/texture/combiner state (`core/t64_digest.c:213-219,529-532`). Guest RDRAM bytes are hashed separately at `core/t64_digest.c:282-283`.
- No current helper centralizes RDRAM write notifications. For a new byte-addressed coverage sidecar, invalidate only after successful CPU/masked/cache/PI/SP backing commits; author RDP fill/copy/raster outputs where the output pixel address is already known. Keep cached stores pending until their backing writeback. Do not equate the existing triangle sample plane with per-memory coverage.

## Address Aliases and Implementation Constraints

- Guest RDRAM is a byte array. CPU bus writes select big-endian physical byte lanes; partial stores provide masks over aligned 4- or 8-byte containers (`core/t64_bus.c:704-798`). A 32-bit store or writeback can overlap two current 16-bit RDP pixels; an 8-byte partial/full store can overlap four. Coverage mutation must derive affected logical entries from byte address and selected lanes, independent of the CPU access width.
- Current RDP fill, texture-copy, and triangle destination paths require 16-bit RGBA color images. The bus can still modify those same bytes through 8/16/32/64-bit CPU views and DMA. Any additional 16/32-bit hidden-coverage field mapping is not present in code and must be named as a deterministic software policy or sourced before implementation; do not infer physical packing.
- Make sidecar updates bounded, per-instance, allocation-free during writes, and non-failing after the backing mutation is accepted. Include all future-affecting sidecar state in the matching profile's allocation/reset and canonical digest path.
