# Title: behavior specification

Single behavior authority of the Phase 12 title (plan 12-02). Two artifacts are derived from
this text and from nothing else: the independent oracle `fixtures/title/title_oracle.py` (which
produces every expected value before any guest exists) and the guest source
`fixtures/title/title.S` (plan 12-03). A value that is not written here is not specified; a
value that has to change is changed here first, in the decision record of the phase
(`PIN-IMPACT.md`, rows DR-01 to DR-07) and then in the oracle and the guest.

Evidence tier: authored, rights-cleared homebrew behavior of one named software profile
(`ntsc-cart-4m-openipl3-rdram-b-t1-si-v2-s32k`). Every figure below is a software-profile policy
value or an authored choice. No compatibility, accuracy, hardware, real-time, latency or
throughput claim is made. No other emulator's output is consulted and no oracle material (D5)
is involved.

## TS-1 What the title is

One screen of 128 by 96 pixels, one 16 by 16 filled square on a flat background, moved by the
D-pad or the stick of port 0, one fixed tone burst on A, one save slot in SRAM that keeps the
position and the press count, B resets the position and Start saves and ends the run. The
guest never takes an interrupt, never reads a wall clock and never counts instructions to wait:
it is locked to the video field by polling (TS-5). Nothing else is part of the title: no Z, no
texture, no RSP microcode, no TLB, no library. The guest is at most about 600 lines of assembly.

## TS-2 Identity

- Profile: `ntsc-cart-4m-openipl3-rdram-b-t1-si-v2-s32k` (DR-01).
- ROM stems: `phase12-title-s32k` (the title) and `phase12-title-refused-s32k` (the refused-frame
  variant, TS-13, built with the assembler definition `T64_TITLE_REFUSED=1`).
- Entry `0x80000400`, clock `0xf`, crc2 `0`, completion symbol `t64_title_completion`: the
  address of the `break` that ends a run (TS-11). The run completes when the guest executes it.
- The guest is built from authored source with the pinned assembler; the ROM is never committed.

## TS-3 Screen and video registers

Framebuffer: RDRAM `0x00100000`, 128 by 96 pixels, 32-bit RGBA, stride 512 bytes, 49,152 bytes
per frame (DR-02). One video packet is exactly the 49,152 bytes of the framebuffer in memory
order R, G, B, A (the scan-out of VI mode 3 passes the bytes through; the byte four value 0xff
expands to alpha 255 by the rule of `docs/spec/vi.md`).

The guest programs the VI before the first field and writes `STATUS` last. The register values
are, with the offsets of `docs/spec/vi.md`: `ORIGIN` 0x00100000, `WIDTH` 128, `INTR` 2,
`V_SYNC` 525, `H_SYNC` 3093, `H_START` 128 (start 0, end 128), `V_START` 192 (half-lines,
start 0, end 192: 96 rows), `X_SCALE` 0x400, `Y_SCALE` 0x400, `STATUS` 0x303 (mode 3, nearest
anti-alias bits). The write of `STATUS` is the VI enable.

## TS-4 Time base: fields, the nominal origin and the polls

Guest ticks run at 62,500,000 per second; the VI source clock is 48,681,812 Hz
(`docs/spec/vi.md`, clock and boundary policy). With `H_SYNC` 3093 and `V_SYNC` 525 a field is
`(3093 + 1) * 525 / 2 = 812,175` source cycles. The field boundary `k` (k = 0, 1, 2, ...) is

    B(k) = T0 + ceil(k * 812,175 * 62,500,000 / 48,681,812)

evaluated in exact rational arithmetic (the ceiling rule of `docs/spec/vi.md`: the fraction a
rounding consumed is carried, so the boundaries are the ceilings of the exact multiples, not
multiples of one rounded period). `T0` is the guest tick of the VI enable (TS-3). B(0) = T0;
the first field boundary is T0 + 1,042,709 (the figure `docs/spec/vi.md` gives for a standard
field). The VI emits one video packet at every boundary B(k), k >= 1.

Nominal origin (an assumption, not a measurement): `T0 = 550,000`. The open IPL3 boot runs
about 530,000 ticks before the guest starts and the guest enables the VI a few thousand ticks
later; a guest whose real `T0` lies within 100,000 ticks of the nominal value gives the same
expectations, because every scripted input stamp lies at least 200,000 ticks from every
boundary (TS-15). The guest is required to have programmed the VI and entered its loop
before the first boundary. Plan 12-03 measures the real `T0`; a value outside the 100,000 band
is a change to this section first (the scripts are regenerated by the oracle).

Poll `p` (p = 1, 2, ...) is the controller read that follows the pending bit of field `p - 1`
(TS-5). It takes place at about `B(p - 1)` plus a delay between 4,000 and 60,000 ticks (the
pending bit rises 3,973 ticks after the field start, then one RD64B transfer with one state
command costs 10,876 ticks until the controller is sampled, `docs/spec/si-pif-controller.md`).
The controller latch gives poll `p` the last input event stamped strictly before the sampling
tick (`docs/spec/si-pif-controller.md`, input latch; `docs/spec/api.md` section 10.2). Because
no stamp lies within 200,000 ticks of a boundary, poll `p` sees exactly the last event stamped
before `B(p - 1)`. Poll 1 therefore sees only events stamped before `T0 - 200,000`: none in
any committed script, so poll 1 is neutral.

The frame rendered after poll `p` is the video packet emitted at `B(p)`. Scripted events are
stamped at field midpoints: event field `j` (j = 0, 1, ...) is stamped at
`B(j) + (B(j + 1) - B(j)) // 2` and is first seen by poll `j + 2`.

## TS-5 Frame lock

The guest loop, after the setup of TS-12 and the VI enable:

1. Wait until bit `0x08` (VI pending) of `MI_INTERRUPT` is set, with `Status.IE` clear and no
   exception handler; then write `VI_CURRENT` (any value) to clear it (DR-03).
2. Poll the controller (TS-6) once.
3. If the Start button is set, run the end sequence (TS-11) and stop.
4. Apply the input rule (TS-7), start a burst if the rule asks for one (TS-8) and render one frame
   (TS-9). Go to step 1.

The render of one frame is complete before the next boundary. No delay loop counts
instructions. Exactly one controller poll and at most one render happen per field.

## TS-6 Controller poll

At setup the guest writes one 64-byte PIF frame with a write DMA (parse request in byte 63):
byte 0 `0x01` (transmit one byte), byte 1 `0x04` (receive four bytes), byte 2 `0x01` (state
command), bytes 3 to 6 `0xff`, byte 7 `0xfe` (end), bytes 8 to 62 zero, byte 63 `0x01`. Each
poll is one read DMA of the PIF image; the four state bytes are bytes 3 to 6 of the returned
image: the buttons high byte, the buttons low byte with bits `0x80` and `0x40` cleared, then the
X and Y axes as unsigned bytes of the signed values (`docs/spec/si-pif-controller.md`). Button
bits of the 16-bit word: A 15, B 14, Z 13, Start 12, Up 11, Down 10, Left 9, Right 8; the
title reads only these eight and the two axes; every other button is ignored. The stick Y axis
is positive up. The logical pad of a poll is (buttons, X, Y).

## TS-7 Input rule

State: position (x, y), press count `n` (unsigned 32-bit), `previous A` (a flag, clear at boot).
Initial position (56, 40), `n` = 0, unless the boot load restores a slot (TS-12). For every poll
that does not see Start:

1. If B (bit 14) is set: the position becomes (56, 40) and nothing moves. Otherwise movement:
   `right` is set when Right (bit 8) is set or X >= 16; `left` when Left (bit 9) is set or
   X <= -16; `down` when Down (bit 10) is set or Y <= -16; `up` when Up (bit 11) is set or
   Y >= 16 (the stick threshold is an absolute axis value of at least 16; a value of 15 or
   -15 is inside it and does nothing). Then `dx = 2 * right - 2 * left` and
   `dy = 2 * down - 2 * up` (screen y grows downward, so Down and a negative stick Y add
   to y; D-pad and stick in the same direction still move 2 pixels, not 4; opposite directions
   cancel). The position becomes (clamp(x + dx, 0, 112), clamp(y + dy, 0, 80)).
2. A press edge: A (bit 15) set now and `previous A` clear. On an edge `n` is increased by 1 and
   a burst is requested (TS-8). Independently of the edge, `previous A` becomes the A bit of this
   poll.

Z and every other button have no effect. A poll that sees Start changes none of this state
(TS-11).

## TS-8 Tone burst

A burst is two audio DMA descriptors, each of 2,048 bytes taken from the same tone table, so a
burst yields two audio packets of 2,048 bytes with identical bytes. The tone table is 512
stereo frames of 4 bytes; frame `f` (f = 0 to 511) is the sample +0x2000 (bytes `20 00`) when
`f mod 64 < 32` and -0x2000 (bytes `e0 00`) otherwise, the same sample in the left and the
right channel: a square wave of period 64 frames and amplitude 0x2000. `DACRATE` is 1103 and
`BITRATE` is 15 (valid: `1104 >= 66 * 16`, `docs/spec/audio-interface.md`); the guest enables
the AI at setup (`AI_CONTROL` 1) and queues the descriptors on a burst request. A burst plays for
about 1,451,000 guest ticks (1,024 frames at 1,417 ticks).

The guest submits a burst only when `AI_STATUS` shows neither busy (bit 30) nor full (bit 31); a
press edge while a burst is still playing only counts. The oracle never produces that case: it
refuses a script whose A press edges are fewer than 3 polls apart (TS-15), which keeps every
burst finished before the next.

## TS-9 Render

One frame is the following RDP list, built in uncached RDRAM and run with the DPC registers; the
guest waits for the DP interrupt bit of `MI_INTERRUPT` (set the DP mask bit first, clear it by an
`MI_MODE` write), as `fixtures/rdp/fill.S` does:

1. SetColorImage: format RGBA, size 32 bit, width 128, address 0x00100000.
2. SetScissor: (0, 0) to (128, 96).
3. SetOtherModes `0x2f300000, 0x00000000` (fill cycle type).
4. SetFillColor `0x203060ff` (background).
5. FillRectangle over the whole screen: lower right (127, 95) inclusive, upper left (0, 0).
6. SetFillColor `0xf0c020ff` (square).
7. FillRectangle (x, y) to (x + 15, y + 15) inclusive: lower right word coordinates in 10.2 fixed
   point `(x + 15) * 4` and `(y + 15) * 4`, upper left `x * 4` and `y * 4`.
8. SyncFull.

The expected frame is therefore: every pixel `20 30 60 ff`, except the 256 pixels with
`x <= px <= x + 15` and `y <= py <= y + 15`, which are `f0 c0 20 ff`. The frame digest is the
SHA-256 of the 49,152 bytes.

## TS-10 Transcript

The guest prints ASCII lines through the ISViewer window, at most 4,096 bytes in all. Hex digits
are lower case. Two line forms exist:

- boot line, printed once during setup only when a slot was restored (TS-12):
  `L xx yy cccccccc` and a line feed (17 bytes): `xx` the restored x, `yy` the restored y
  (two digits each) and `cccccccc` the restored press count (eight digits);
- end line, printed once by the end sequence (TS-11): `S xx yy cccccccc pp` and a line feed
  (20 bytes): the position and the press count at that time and `pp`, the number of controller
  polls made including the poll that saw Start (two digits).

## TS-11 End sequence and completion

The poll that sees Start (bit 12) ends the run without applying TS-7. The end sequence:

1. Write the 16-byte save slot (TS-12) from the current position and press count.
2. Print the end line (TS-10).
3. Execute `break` at the symbol `t64_title_completion`. Completion is the stop reason
   guest-completion at that instruction; the title does nothing afterwards.

A run that never sees Start never completes by itself; the host ends it. The first poll that
sees Start renders no frame, so the number of video packets of a completed run equals the
number of polls before the Start poll.

## TS-12 Save slot and boot load

The save device is SRAM (32,768 bytes, blank content is zero, `docs/spec/save-media.md`). The
slot is the first 16 bytes at SRAM offset 0, four big-endian 32-bit words: magic `0x54363454`
(ASCII `T64T`), x, y, press count. Blank bytes follow; the title writes nothing else. The slot
is written and read with one 16-byte PI DMA.

Boot load: at setup, before the first frame, the guest reads the slot. It restores the state
only when the magic matches, x <= 112 and y <= 80; otherwise the defaults of TS-7 stay and no
boot line is printed. When it restores, it prints the boot line (TS-10) and continues with the
restored position and press count; `previous A` stays clear.

## TS-13 Refused-frame variant

The ROM built with `T64_TITLE_REFUSED=1` writes the single word `0x2f000000, 0x00000000`
(one-cycle) in step 3 of TS-9 instead of the fill mode. The RDP refuses the packet, the
framebuffer stays all zero and the guest never leaves its wait for the DP interrupt. Expected
behavior of that ROM (DR-04, DR-08): every video packet is the blank frame (49,152 zero
bytes), no audio packet, no transcript text, no save write and no completion; a run ends only
at the tick cap and is not a pass. The blank digest is the SHA-256 of 49,152 zero bytes.

## TS-14 Scenarios

Each scenario is a script in the `t64.input` v1 form (`schema` "t64.input", `schema_version` 1,
events with the keys `buttons`, `port`, `tick`, `x`, `y`; `tick` a decimal string; port 0). The
oracle generates the scripts (`--emit-inputs`); an event row lists its field `j` (TS-4),
`buttons` and the axes. Buttons are written as names: A, B, S (Start), U, D, L, R.

| Scenario | Used by | Events (field j: pad) | Polls to Start |
|----------|---------|-----------------------|----------------|
| short | runner | 0: R+A, 1: B, 2: S | 4 (3 packets) |
| short-wrong | runner wrong-input control | 0: L+A, 1: B, 2: S | 4 (3 packets) |
| long | consumer and pump | 0: R, 1: R+D, 2: stick x 40, 3: stick x 15 y -15, 4: A+U, 5: U+L, 6: neutral, 7: A and stick x -100 y -50, 8: B, 9: R+D, 10: R+D, 11: S | 13 (12 packets) |
| shifted | consumer and pump wrong-input control | the long events at field j + 1 | 14 (13 packets) |
| persist | consumer persistence | no events; boots from the save image written by the long run, 3 packets | none (3 packets) |

Short scenarios keep their Start poll at poll 4 or earlier: poll 4 happens near
`B(3) + 60,000 = 3,738,126` ticks and completion follows within a few thousand ticks, below the
runner guest cap of 4,000,000 ticks. A fourth rendered field would need `B(4)`, 4,720,834, which is
above it.

## TS-15 Oracle constraints (the oracle exits 2 when one is broken)

- Strict grammar: schema, closed keys, decimal `tick` without a sign or a leading zero, port 0,
  buttons 0 to 65,535, axes -128 to 127, ticks never going backwards, at most 4,096 events and
  65,536 bytes.
- Every stamp lies at least 200,000 ticks from every boundary B(k), k >= 0 (the margin of
  DR-05; a stamp closer is ambiguous because the poll sampling tick is known only to about
  60,000 ticks).
- A script of the short kind has its Start poll at poll 4 or earlier (at most 3 rendered
  fields, TS-14).
- Two A press edges are at least 3 polls apart, and the last A press edge is at least 2 polls before
  the Start poll, so every burst has finished (TS-8).
- A script run to completion must press Start; a script that never presses Start, or presses it at
  poll 1, is refused.

## TS-16 Not specified here

Pump pacing, host mapping of a physical controller, the host window and any wall-clock behavior
belong to the host plans. The packet metadata (ticks, serial numbers) of video and audio is not
part of the expectations; only the packet bytes, the save bytes and the transcript are.
